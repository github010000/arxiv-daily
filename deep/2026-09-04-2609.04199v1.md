## 한 줄 요약
이 논문은 자연어로 적은 함수 명세를 컴파일 시점에 대형 teacher model들이 만든 예제로 작은 LoRA adapter에 학습시켜, 실행 시점에는 원격 대형 모델 호출 없이 재사용할 수 있는 local neural function으로 만드는 "compile by training"을 제안하고, PAW의 빠른 컴파일러가 실패한 FuzzyBench-Hard에서 semantic accuracy 83.6%를 달성했다.

## 핵심 개념 풀이

### natural-language specification
이 논문에서 specification은 "함수가 무엇을 해야 하는지"를 자연어로 적은 설명이다. 예를 들어 "이메일 제목이나 본문을 보고, 서명이 오늘 중으로 필요하다는 내용이면 immediate로 분류하고 뉴스레터면 wait로 분류하라"는 식이다. 이는 코드가 아니라 의도를 서술한 문장이기 때문에, 사람은 금방 이해하지만 규칙으로 옮기기는 어렵다. 컴파일러는 이 자연어 specification을 받아서 실제로 입력을 출력으로 바꾸는 함수를 만들어야 한다.

### teacher model과 synthetic supervision
teacher model은 컴파일할 때만 호출되는 대형 언어 모델이다. specification을 주면 그 함수가 어떻게 동작해야 하는지를 보여주는 입출력 쌍을 만들어 낸다. 예컨대 "arXiv 식별자를 뽑되 /abs/ 링크는 무시하라"는 specification이 있으면, teacher는 /pdf/ 링크와 /abs/ 링크가 섞인 문장을 입력으로 만들고 출력으로는 ["2607.02512"] 같은 올바른 식별자를 만든다. 이렇게 사람이 직접 레이블을 붙이지 않고 큰 모델이 만든 학습 데이터를 synthetic supervision이라고 부른다. 데이터가 생성된 뒤에는 작은 모델을 학습시키는 정답 신호로 쓰인다.

### frozen interpreter
이 시스템은 함수마다 별도의 전체 모델을 학습시키지 않는다. 대신 Qwen3-0.6B라는 작은 언어 모델 하나를 공유하면서 그 모델의 가중치는 고정해 둔다. 이 고정된 모델을 interpreter라고 부르는 이유는, 이 모델이 실제로 입력을 읽고 출력을 만들어 내는 실행 엔진 역할을 하기 때문이다. 마치 CPU가 프로그램을 실행하듯이, frozen interpreter는 adapter와 prompt가 지정한 대로 토큰 확률을 계산한다. 이렇게 하면 함수마다 전체 모델을 저장할 필요가 없고, 사용자별로 가벼운 부품만 바꿔 끼울 수 있다.

### LoRA adapter
LoRA adapter는 거대 모델 전체를 다시 학습하지 않고, 일부 linear layer에 아주 작은 추가 행렬만 얹어서 동작을 바꾸는 방식이다. 어댑터는 원래 모델의 가중치를 직접 수정하지 않고, low-rank 행렬 곱으로 표현되는 작은 변화량을 더한다. 여기서 rank를 작게 잡으면 저장해야 하는 파라미터 수와 학습 비용이 크게 줄어든다. 이 논문에서는 rank 64짜리 LoRA adapter를 사용하며, 이 adapter만 함수마다 저장하면 된다. 실행 시에는 같은 frozen interpreter에 이 adapter를 얹어서 그 함수에 특화된 출력을 만든다.

### Program-as-Weights와 amortized compiler
Program-as-Weights는 neural program을 소스 코드가 아니라 가중치로 저장한다는 관점이다. 즉 adapter의 weight 자체가 프로그램이며, 같은 frozen interpreter 위에서 그 weight를 바꾸면 다른 함수가 된다. 기존 PAW 시스템에는 amortized compiler가 있었는데, 이것은 specification을 한 번 forward pass로 읽고 adapter weight를 바로 예측한다. amortized라는 표현은 일반적인 컴파일러 학습에 큰 비용을 한 번 지불해 두면, 이후 개별 함수를 컴파일할 때는 아주 적은 계산만 쓴다는 의미다. 빠르지만 모든 specification에 같은 계산량만 들이기 때문에 어려운 명세에서는 품질이 떨어진다.

### LLM Exact Match
LLM Exact Match는 줄여서 LEM이라고 하며, 모델 출력이 참조 출력과 글자 단위로 똑같은지가 아니라 의미적으로 맞는지를 LLM이 판단하는 지표다. 예를 들어 JSON에서 공백이나 키 순서만 다른 두 출력은 exact match에서는 틀린 것으로 처리되지만, 사람이 보면 같은 답이다. LEM은 specification과 입력, 참조 출력, 모델 출력을 모두 LLM judge에게 주고 "이 예측이 명세에 비추어 의미적으로 올바른가"를 묻는다. 따라서 여러 개의 올바른 표현이 가능한 fuzzy한 텍스트 함수를 평가하는 데 더 적합하다.

## 문제의식

많은 반복적인 텍스트 함수는 동작을 설명하기는 쉽지만 규칙으로 구현하기는 어렵다. 예를 들어 "Signature needed by EOD"라는 문장을 immediate로 분류하고, 뉴스레터를 wait로 분류하는 이메일 분류 함수는 사람에게는 명확하다. 하지만 이메일에는 같은 의도를 다르게 표현하는 수많은 변형이 있기 때문에 키워드 규칙이나 정규식으로 짜면 금방 부서진다. "EOD", "오늘 중", "end of day" 같은 표현을 모두 나열하는 방식은 유지보수가 어렵고, 새 표현이 나올 때마다 규칙을 고쳐야 한다.

반대로 모든 입력을 범용 원격 LLM에 보내는 방법도 있다. 그러나 이메일 수천 통을 처리할 때 매번 네트워크를 타고 원격 모델을 부르면 응답 지연이 누적되고, 사용량에 따라 비용이 계속 발생한다. 또 서비스 제공자의 API가 바뀌거나 장애가 나면 전체 기능이 멈출 수 있다. 이처럼 전통적인 규칙 코드와 매 호출마다 큰 모델을 부르는 방식 사이에는 실제로 곤란한 틈이 있다.

기존 PAW의 fast amortized compiler는 이 틈을 한 번에 메우려고 했다. specification을 받아 단 한 번의 forward pass로 adapter weight를 예측하므로 컴파일이 몇 초면 끝난다. 그런데 이 방법은 어려운 함수에서 정확도가 크게 떨어졌다. 논문이 만든 FuzzyBench-Hard는 fast compiler가 exact match를 하나도 내지 못한 specification들로 구성된 부분집합인데, 그 위에서 fast compiler의 semantic accuracy는 0.224에 불과했다. 즉 빠르기는 하지만 어려운 명세에서는 사실상 제대로 동작하지 않는 경우가 많았다.

따라서 필요한 것은 대형 모델을 아예 없애는 대신, 대형 모델의 지식을 한 번만 써서 작은 로컬 함수를 잘 만드는 과정이다. 이 논문은 그 과정을 컴파일이라는 소프트웨어 빌드 단계로 바꾸려고 한다.

## 핵심 아이디어

이 논문의 핵심은 대형 teacher model을 실행 시간의 의존성에서 컴파일 시간의 도구로 옮기는 것이다. 즉 함수를 만들 때만 큰 모델을 부르고, 만들어진 함수는 이후 로컬에서 teacher 없이 실행되게 한다. 이렇게 하면 원격 호출에서 오는 반복 비용과 지연, 외부 서비스 의존을 끊을 수 있다. teacher model은 specification을 읽고 입력 $x$와 정답 출력 $y$의 쌍을 대량 생성하는 "가르치는 역할"만 한다.

이 아이디어가 문제를 푸는 이유는 specification이라는 추상적인 설명을 concrete한 학습 신호로 바꾸기 때문이다. 자연어 명세는 사람은 이해할 수 있지만 gradient descent에 직접 넣을 수 없는 모호한 정보인데, teacher가 만든 입출력 쌍은 작은 모델이 실제로 학습할 수 있는 형태다. 이 신호로 작은 adapter를 학습시키면, 큰 모델의 일반 언어 이해 능력을 빌려서 특정 함수를 local에 재현할 수 있다.

또한 느린 fine-tuning을 처음부터 하지 않고, PAW의 fast compiler가 예측한 adapter weight를 초기값으로 쓴다. fast compiler는 몇 초 만에 대략적인 프로그램을 만들어 주므로, 이후 학습은 틀린 부분만 고치는 refine 과정이 된다. 이것은 정확도와 컴파일 시간 사이에서 두 극단을 잇는 절충점을 만든다. fast compiler는 초 단위지만 정확도가 낮고, 처음부터 전체를 학습하면 더 오래 걸리지만, warm start를 쓰면 1분 내외로 큰 정확도 향상을 얻을 수 있다.

마지막으로 컴파일된 결과를 일반 소프트웨어처럼 다룰 수 있다는 점이 중요하다. adapter와 scaffold, 원래 specification을 묶은 artifact는 저장하고 버전을 붙이고 캐시하고 다른 코드와 조립할 수 있다. 따라서 neural function이 일회성 모델 호출이 아니라 애플리케이션의 일반 부품이 된다.

## 방법

시스템이 제공하는 인터페이스는 다음과 같다.

```math
p_s = \texttt{Compile}(s), \quad \hat{y} = \texttt{Run}(p_s, x)
```

여기서 $s$는 자연어 specification, $p_s$는 컴파일된 프로그램, $x$는 실행 시점에 들어오는 새 입력, $\hat{y}$는 프로그램의 출력이다. 이 형태의 핵심은 컴파일과 실행을 분리한다는 점이다. 한 번 만든 $p_s$는 이후 입력 $x$에 반복해서 사용할 수 있고, 실행할 때 teacher model을 다시 부르지 않는다.

컴파일의 첫 단계는 teacher model을 불러 학습 데이터셋을 만드는 것이다.

```math
D_s=\{(x_i,y_i)\}_{i=1}^{n}\sim T(s)
```

여기서 $T(s)$는 specification $s$를 받은 teacher model이 생성하는 입출력 쌍의 분포를 뜻한다. 각 $x_i$는 함수가 처리할 입력이고 $y_i$는 teacher가 정답으로 제시한 출력이다. public service에서는 저렴한 teacher가 대부분의 예제를 만들고, 더 큰 teacher가 보완적인 supervision을 추가한다. 교사 요청은 JSON 형식으로 주고받으며, 컴파일러는 응답을 검증해서 형식이 잘못되었거나 배치가 불완전한 예제는 학습에 넣지 않는다.

다음으로 학습 대상이 되는 모델을 정한다. 모든 함수는 frozen Qwen3-0.6B interpreter를 공유한다. 이 interpreter는 일반적인 언어 모델이지만 가중치를 고정해 두고, 함수마다 LoRA adapter $\theta_s$만 바꾼다. LoRA는 일부 linear layer에 low-rank 행렬 변화를 더하는 방법이다. rank 64와 alpha 16을 쓰는데, rank는 adapter가 학습하는 저차원 표현의 차원 수를 정하고 alpha는 그 변화를 원래 출력에 반영하는 크기를 조절한다. 따라서 각 함수의 실질적 프로그램은 이 adapter 하나다.

또한 실행에 필요한 scaffold $r_s$가 있다. scaffold는 사용자의 자유 형식 specification을 정형화된 task instruction과 예시로 바꾸고, 실행 시 입력이 들어갈 자리를 남겨 둔 prompt template이다. PAW의 fast amortized compiler가 초기 adapter weight $\theta_s^{(0)}$과 scaffold $r_s$를 예측해 준다. 이 예측은 몇 초면 되고, 이후 refine 학습의 출발점이 된다.

이제 teacher가 만든 데이터로 다음 손실을 최소화한다.

```math
\mathcal{L}(\theta_s)=\sum_{(x,y)\in D_s}-\log p_{\theta_s}(y\mid r_s(x))
```

여기서 $r_s(x)$는 입력 $x$를 scaffold에 넣어 만든 prompt이고, $p_{\theta_s}(y\mid r_s(x))$는 adapter $\theta_s$를 얹은 frozen interpreter가 그 prompt를 보고 정답 출력 $y$를 generate할 조건부 확률이다. $-\log$를 취하는 이유는 올바른 출력에 확률을 더 많이 줄수록 손실이 작아지도록 만들기 위해서다. 이 합을 최소화하면 adapter는 teacher가 만든 예제들에서 정답을 잘 예측하도록 특화된다.

학습이 끝나면 adapter $\theta_s$, scaffold $r_s$, 원래 specification, interpreter metadata를 하나의 프로그램 $p_s$로 packaging한다. 다운로드한 .paw artifact는 이 부품들을 담고 있다. 이후 local SDK는 새 입력을 scaffold와 adapter에 결합해 frozen interpreter를 실행하며, 미래의 입력을 PAW 서비스나 teacher에게 보내지 않는다.

컴파일을 대화형 서비스로 제공하기 위해 시스템은 여러 단계를 겹쳐 실행한다. 순차적 방식은 모든 teacher 응답이 도착한 뒤에 모델을 로드하고 학습을 시작하지만, 이 논문의 배포된 경로는 teacher 요청, 모델 로딩, 학습을 동시에 시작한다. 학습은 첫 배치에 필요한 예제가 준비되는 즉시 시작되고, 합성이 학습을 따라잡지 못할 때만 block된다. teacher 응답은 도착 시간이 제각각이므로 scheduler는 이전 배치에 필요한 빈 자리에 새 예제를 우선 배정한다.

서비스 아키텍처는 API, 공유 큐, GPU worker를 분리한다. API는 각 compile job을 영속적으로 기록하고, 큐는 job을 사용 가능한 GPU worker에게 넘긴다. worker는 teacher 캐시를 먼저 확인하고 중복되는 teacher 출력을 재사용하며, 완성된 artifact는 중앙 저장소에 저장된다. 사용자 인터페이스는 컴파일을 막는 form 제출이 아니라 백그라운드 software build로 취급한다. 사용자는 제출 후 다른 페이지를 계속 탐색하면서 큐 위치와 training progress를 볼 수 있다.

## 왜 성립하는가

이 논문은 formal proof를 제시하지 않는다. 대신 compile by training이 빠른 one-shot prediction보다 더 잘 맞는 이유를 학습 과정과 실험 결과로 뒷받침한다. 핵심 근거는 teacher가 만든 synthetic dataset이 specification의 의미를 concrete한 학습 신호로 옮긴다는 데 있다. teacher가 specification을 잘 이해하면 그 이해가 수많은 입출력 쌍에 반영되고, gradient descent는 그 신호를 adapter weight에 복사한다.

이 과정이 소수의 예제보다 잘 되는 이유는 frozen interpreter가 이미 일반 언어 모델로 학습되어 있기 때문이다. adapter는 언어 자체를 처음부터 배우는 것이 아니라, 이미 언어를 아는 모델의 행동을 특정 함수에 맞게 조정하는 작은 patch를 학습한다. 따라서 teacher가 준 입출력 쌍만으로도 함수의 차이를 반영하기에 충분하다.

또한 fast compiler의 warm start가 학습을 처음부터 탐색하지 않게 만든다. $\theta_s^{(0)}$은 이미 그 specification에 어느 정도 맞춰진 초기값이므로, 학습은 엉뚱한 지역에서 시작하지 않고 정답 근처에서 시작한다. teacher-generated 데이터로 다시 학습하면 fast compiler가 잘못 해석한 부분만 골라서 고칠 수 있다. 이 때문에 1분 내외의 짧은 학습으로도 큰 정확도 상승이 가능하다.

실험적 근거도 이 주장을 뒷받침한다. FuzzyBench-Hard에서 fast compiler의 mean LEM은 0.224였고 compile by training은 0.836이었다. 이는 0.612 absolute 상승이다. controlled sweep에서는 teacher mixture를 바꾸자 LEM이 0.746에서 0.851로 올랐고, unique pair 수를 늘리자 0.821에서 0.866까지 올랐다. 이는 teacher가 만드는 supervision의 질과 양이 실제 정확도에 영향을 준다는 것을 보여 준다.

대화형 사용이 성립하는 이유는 시스템 설계에 있다. teacher synthesis가 전체 latency를 지배하고 개별 training step이 그보다 빠르므로, 합성을 학습과 겹쳐 실행하면 critical path가 짧아진다. 4개 job을 동시에 제출한 load test에서 평균 queue wait이 1.01초에 불과했고 worker utilization도 고르게 유지되었다. 즉 1분 내외의 compile도 사용자가 기다리면서 서비스가 막히는 경험을 만들지 않는다.

## 구체적 예시

개발 명세 집합에서 teacher와 데이터 양을 바꾸며 LEM을 비교한 Table 1을 따라가 보자. LEM은 judge가 의미적으로 맞다고 판단한 비율이므로, 0.746은 100개 예측 중 약 75개가 올바르다는 뜻이다. 첫 번째 행은 저렴한 GPT-5.4-mini teacher만 써서 서로 다른 입출력 쌍 3600개를 만든 경우다. 이 unique pair들을 반복해서 6400개짜리 training set으로 구성하고 학습시켰을 때 mean LEM은 0.746이었다. 약 4개 중 3개를 맞춘 것이므로, 작은 teacher 하나만으로는 함수의 어려운 부분까지는 충분히 가르치지 못했다.

두 번째 행은 teacher 구성을 바꾼 경우다. 여전히 unique pair의 총수는 3600개로 유지하되, 2400개는 GPT-5.4-mini가 만들고 1200개는 더 큰 GPT-5.5가 만든 2:1 mixture를 썼다. 결과적으로 mean LEM은 0.851로 올랐다. 0.746에서 0.851로의 상승은 0.105 absolute increase이며, 상대적으로는 약 14% 더 많은 경우를 의미상 맞추는 셈이다. 큰 teacher가 만든 1200개가 작은 teacher가 놓치거나 잘못 해석한 예제를 보강했기 때문으로 해석할 수 있다.

데이터 크기를 올리는 sweep도 같은 표에 있다. unique pair가 1440개일 때 LEM은 0.821이었고, 2400개일 때 0.836, 3600개일 때도 0.836으로 유지되었다. 그 뒤 7200개로 늘리자 0.866으로 다시 올랐다. 2400개와 3600개 사이에 변화가 없는 구간은 그 범위에서는 데이터 증가의 효과가 작았음을 보여 준다. 반면 7200개에서의 상승은 데이터 다양성이 충분히 커질 때 성능이 한 단계 더 좋아질 수 있음을 시사한다.

이 표가 흥미로운 이유는 main 실험의 0.836이라는 숫자만 보고서는 알 수 없는 비용-품질 절충을 직접 보여 주기 때문이다. teacher mixture를 바꾸면 컴파일 비용과 데이터 생성 시간이 늘지만 LEM이 오르고, unique pair 수를 늘리면 더 많은 교사 호출과 학습 시간이 필요하지만 LEM이 오른다. 따라서 0.836이라는 결과는 그냥 우연한 숫자가 아니라 teacher 선택과 데이터 규모에서 가능한 여러 설정 중 하나의 결과다.

## 실험과 결과

평가에는 FuzzyBench-Hard라는 부분집합을 사용했다. 이 집합은 원래 PAW의 fast amortized compiler가 exact match를 하나도 내지 못한 specification들로 구성되어 있다. 즉 처음부터 어려운 함수들만 모은 벤치마크다. 정확도는 LEM으로 측정했고, 판정에 쓴 GPT-5.5 judge는 128개의 사람 레이블과 비교했을 때 accuracy 0.977, Cohen's kappa 0.946을 기록했다. 0.977은 judge가 사람의 판정과 거의 일치한다는 뜻이고, kappa 0.946은 우연히 일치할 가능성을 보정해도 매우 높은 신뢰도를 가진다는 뜻이다.

main 결과에서 fast compiler는 평균 LEM 0.224를 기록했고, compile by training은 0.836을 기록했다. 0.224는 약 5개 중 1개만 의미상 맞았다는 뜻이고, 0.836은 약 6개 중 5개를 맞췄다는 뜻이다. 따라서 이 0.612 absolute 상승은 단순한 몇 퍼센트 개선이 아니라, 대부분 틀리던 수준에서 대부분 맞추는 수준으로 바뀐 큰 변화다. 이 비교에 사용한 fast compiler는 exact match는 0이었지만 LEM은 0.224였으므로, 문자 단위 비교가 아니라 의미 단위 비교가 필요하다는 점도 확인된다.

더 높은 정확도에는 더 긴 컴파일 시간이 필요했다. 같은 대표 specification을 cold compile할 때 compile by training은 50.9초가 걸렸고, fast compiler는 3.5초가 걸렸다. 50.9초라는 값은 B300 GPU 기준이며, H200에서는 68.2초, RTX GPU에서는 99.2초가 걸렸다. 하드웨어가 약할수록 학습 시간이 늘지만, 그래도 수 초에서 수십 초가 아니라 1분 내외라는 점이 중요하다. 이 비용은 함수마다 한 번만 지불하면 되는 build cost다.

서비스 부하 실험에서는 네 개의 compile job을 동시에 제출했을 때 평균 큐 대기 시간이 1.01초에 불과했다. worker utilization도 고르게 유지되었다. 이는 1분 내외의 컴파일이 개별 job은 느려도, 여러 job이 들어와도 API가 막히지 않고 GPU worker에 잘 분배된다는 것을 뜻한다. teacher synthesis가 전체 시간을 지배하기 때문에, synthesis와 training을 겹쳐 실행한 설계가 유효했다.

응용 결과도 여러 개 제시되었다. paw-helper는 네 개 사이트를 서빙하는 웹사이트 assistant인데, 30개의 compiled program을 사용하며 그중 28개가 live routing에 참여한다. 이 사례는 여러 neural function이 ordinary code의 retrieval, caching, branch control과 함께 조립될 수 있음을 보여 준다. Avatar Director는 자연어 지시를 action DSL로 바꾸는 프로그램인데, 44개의 hand-authored validation instruction 중 43개에서 기대한 action structure를 만들어 약 97.7%의 성공률을 보였다. Claudish 번역 서비스는 2026년 8월 22일부터 9월 2일 사이에 100,747건의 성공적인 번역 요청을 처리했다. 이 숫자는 정확도 자체를 말하지는 않지만, 컴파일된 함수가 실제 public service에서 상당한 트래픽을 감당했음을 보여 준다.

## 한계

저자가 인정한 가장 명확한 한계는 synthetic supervision이 teacher의 오류를 그대로 물려받을 수 있다는 점이다. teacher model이 specification을 잘못 해석하면 생성된 입출력 쌍 자체에 잘못된 정답이 들어가고, 작은 adapter는 그 잘못을 학습한다. 특히 specification이 모호하거나 전문 영역을 다룰 때 teacher가 plausible하지만 틀린 예제를 만들 수 있다.

따라서 이 시스템은 정확성이 보장되어야 하는 응용에는 부적합하다. 금융, 의료, 안전처럼 출력이 치명적인 영향을 주는 곳에서는 반드시 출력을 검증하거나, 결정을 내리는 경로는 deterministic한 코드가 제어해야 한다. 이 논문도 guaranteed correctness가 아니라 fuzzy한 함수를 위한 도구라는 점을 명시하고 있다.

평가에는 systematic user study가 없다. 애플리케이션 증거는 composition과 structured execution에 초점을 맞추고 있을 뿐, 실제 사용자가 느끼는 품질이나 실패 방식, 장기간 사용에서의 만족도는 아직 측정되지 않았다. 43/44라는 avatar validation은 작은 샘플이고 특정 저자들이 만든 instruction에 가깝다.

또한 FuzzyBench-Hard에서 여전히 약 16.4%는 LEM 기준으로 틀렸다. judge가 의미상 틀렸다고 판단한 예측이 그만큼 남아 있다는 뜻이다. 이는 개선된 결과이지만, 높은 정확도가 요구되는 상황에서는 아직 충분하지 않을 수 있다. 큰 teacher를 더 쓰고 데이터를 더 늘리면 나아질 가능성이 있지만, 컴파일 시간과 teacher 호출 비용이 함께 늘어난다.

컴파일 시간 자체의 의존성도 남아 있다. 실행 후에는 teacher API와 GPU가 필요 없지만, 함수를 만들 때는 여전히 teacher model과 hosted GPU에 의존한다. teacher API가 바뀌거나 장애가 나면 컴파일 단계가 실패할 수 있다. 또한 이 논문의 main latency는 특정 하드웨어와 출시 시점의 교사 모델 기준이므로, 다른 환경에서 50.9초가 그대로 재현된다고 보장할 수 없다.

## 왜 중요한가

이 논문은 대형 언어 모델의 역할을 "매 호출마다 부르는 runtime dependency"에서 "도구를 만드는 tool builder"로 옮기는 관점을 구체적인 시스템으로 보여 준다. 이렇게 되면 반복 비용과 latency가 없어지고, 서비스 제공자에 대한 의존도 줄어들며, 인터넷이 없는 local 실행도 가능해진다. 실무에서는 API 호출 단가가 문제가 되는 대량 텍스트 처리 기능을 로컬에서 돌리고 싶은 경우가 많은데, compile by training은 그 요구에 직접 답한다.

또한 adapter와 scaffold를 일반 소프트웨어 artifact처럼 저장하고 버전을 붙이고 캐시하고 조립할 수 있다는 점이 중요하다. 이는 neural function을 실험실 모델이 아니라 software build의 결과물로 취급하게 만든다. paw-helper의 30개 프로그램 tree처럼, fuzzy한 판단을 여러 compiled function에 나누고 deterministic한 retrieval이나 분기 제어는 기존 코드가 맡기는 구조가 현실에서 가능했다.

속도와 정확도 사이에 새로운 선택지를 만들었다는 점도 후속 연구에 의미가 크다. 기존에는 fast compiler가 초 단위로 adapter를 예측하거나, 아예 별도 모델을 오래 fine-tuning하는 식으로 양극단이 있었다. 이 논문은 fast compiler의 warm start를 쓰고 teacher-generated data로 1분 내외만 더 최적화하면 정확도가 크게 오른다는 점을 실증했다. 앞으로 더 나은 teacher mix, 더 긴 optimization, 더 지능적인 합성 데이터 생성 전략을 얹으면 같은 구조에서 성능을 더 올릴 여지가 있다.

마지막으로 이 접근은 개인이나 조직마다 고유한 fuzzy 함수를 저렴하게 만들 수 있게 한다. 작은 interpreter와 LoRA adapter만 있으면 하나의 명세로부터 번역기, 분류기, 생성기, structured action generator까지 만들 수 있다는 것을 세 가지 demo가 보여 준다. neural function이 보통의 함수처럼 compile되고, 저장되고, 다른 코드에 import되는 시대를 한 단계 앞당긴 결과다.

## 원문 초록

> Many recurring text functions are easy to describe but difficult to implement with rules, while calling a large remote model for every input introduces repeated cost, latency, and dependency on a provider. We present compile by training, which turns a natural-language specification into a reusable neural function. At compile time, teacher models generate task-specific examples that are used to train a small adapter for a compact interpreter. The resulting function runs without the teachers and can be stored, versioned, and composed like ordinary software. On FuzzyBench-Hard, a subset on which the Program-as-Weights fast compiler produced no exact matches, compile by training reaches 83.6% semantic accuracy. This higher accuracy comes with a higher compile-time cost: roughly a minute rather than seconds for the fast compiler. We deploy the compiler in a public interactive service and demonstrate compiled functions in a multi-site website helper, a language-controlled 3D avatar, and a bidirectional English-Claudish translator.
