## 한 줄 요약

Anthropic의 공식 Claude Code VS Code extension이 Cursor Marketplace에서 정품 publisher 신원과 정품 extension ID를 그대로 유지한 채 악성 버전 2.1.313으로 치환되어 배포되었고, 그 코드는 피해자 컴퓨터에 SSH backdoor와 재부팅 후에도 살아남는 지속성 메커니즘을 심으려 시도했다.

## 배경과 핵심 개념

**1) VS Code와 extension, 그리고 marketplace**

VS Code는 Microsoft가 만든 코드 편집기이고, 그 기능은 extension이라는 별도 프로그램 조각을 설치해 확장한다. Extension은 편집기와 별개의 프로그램이지만 사용자 계정 권한으로 실행되며, 편집기 자체의 sandbox 안에서 격리되지 않는다. 그래서 extension을 설치한다는 것은 사실상 "출처를 신뢰하는 사람이 만든 임의의 코드를 내 계정 권한으로 실행하겠다"는 선언과 같다. Marketplace는 이런 extension을 검색하고 내려받고 자동으로 갱신해 주는 중앙 배포소 역할을 한다 (배경).

**2) publisher ID와 version, auto-update라는 신뢰 구조**

Marketplace에서 extension은 "publisher.extension" 형태의 식별자와 version 번호로 구분된다. 이 글에 나오는 `anthropic.claude-code`가 바로 그 식별자이며, 사용자는 이 문자열을 보고 "Anthropic이 만든 것이구나"라고 판단한다. 문제는 대부분의 사용자가 새 version이 올라오면 내용을 검토하지 않고 auto-update로 받아들인다는 점이다. 즉 marketplace의 신뢰 모델은 "코드의 안전성"이 아니라 "publisher 계정의 통제권"에 걸려 있다 (배경).

**3) trojanized, 그리고 공급망 공격**

trojanized는 정품 프로그램을 통째로 가짜로 바꾸는 대신, 정품 껍데기와 신원은 그대로 두고 내부 코드 일부만 공격자 코드로 바꿔치기하는 방식을 말한다. 이 경우 사용자 눈에는 publisher도 이름도 version 흐름도 모두 정상으로 보인다. 이런 유형을 공급망 공격이라고 부르는데, 공격자가 최종 사용자를 직접 속이는 대신 사용자가 신뢰하는 유통 경로를 장악하기 때문이다. 방어자 입장에서 탐지가 어려운 이유는 "비정상적으로 보이는 무언가"가 겉으로 드러나지 않는다는 데 있다 (배경).

**4) SSH, authorized_keys, reverse tunnel**

SSH는 원격 컴퓨터에 접속해 명령을 실행하거나 파일을 주고받는 암호화 프로토콜이다. 공개키 인증 방식에서는 서버 쪽 사용자 홈의 `~/.ssh/authorized_keys` 파일에 등록된 공개키를 가진 사람이 비밀번호 없이 로그인할 수 있다. 따라서 이 파일에 한 줄을 추가하는 것만으로 "영구 출입증"을 만들어 넣을 수 있다. reverse tunnel은 반대 방향으로 동작하는데, 피해자 컴퓨터가 먼저 외부 공격자 서버로 연결을 열어 두면 공격자는 그 연결 통로를 통해 방화벽이나 사설 네트워크 너머의 피해자에게 접근할 수 있다 (배경).

**5) 지속성(persistence)이라는 개념**

악성코드가 한 번 실행되고 사라지면 재부팅 후에는 흔적만 남는다. 그래서 공격자는 "다시 살아나는" 장치를 심는데, 운영체제마다 정해진 방식이 다르다. Windows에는 scheduled task(예약 작업), Linux에는 crontab(정기 실행 목록), macOS에는 LaunchAgent(로그인 시 자동 실행 항목)가 있다. 이 글의 악성 코드는 세 플랫폼 모두에 해당 장치를 심으려 시도했는데, 이는 감염 대상이 개발자 노트북이고 운영체제가 제각각이라는 점을 공격자가 전제했다는 뜻이다 (배경).

**6) VS Code 계열 배포 채널의 파편화**

VS Code 기반 편집기는 여러 갈래로 나뉘어 있고, 각자 다른 extension 배포소를 쓴다. Microsoft의 공식 Visual Studio Marketplace, 벤더 중립을 표방하는 Open VSX, 그리고 각 편집기 업체가 운영하는 자체 marketplace가 있다. 이 사건에서 문제가 된 Cursor는 VS Code를 기반으로 만든 AI 코드 편집기이고, 자체 marketplace를 운영한다. 채널이 여러 개로 쪼개져 있으면 같은 extension이라도 어느 채널에서 받았는지에 따라 안전성이 달라지고, 사고 조사도 채널별로 따로 해야 한다 (배경).

## 글의 내용

기사는 보안 연구자들이 trojanized된 Anthropic 공식 Claude Code extension이 Cursor Marketplace를 통해 "정식 업데이트"처럼 배포되었다고 공개했다고 전한다. 악성 업데이트의 version은 2.1.313이었고, 배포는 extension의 정당한 publisher 신원으로 이루어졌다. 이 때문에 Cursor는 오염된 패키지를 제거하기 위해 marketplace를 일시적으로 폐쇄했다. 기사는 공격자들이 어떤 방법으로 권한 없는 업데이트를 밀어 넣었는지는 아직 불명확하다고 명시한다.

Cursor의 공식 성명은 "Cursor IDE extension marketplace를 통해 접근된 변조된 Claude Code VS Code extension에 영향을 받는 보안 사고를 확인했으며, 영향받은 사용자는 최대 5,000명"이라고 밝힌다. 이어서 해당 악성 version은 Anthropic이 개발한 것이 아니며, marketplace에서 내려받은 다른 extension이나 Grok Bot, Grok, 그리고 자사의 다른 제품에는 영향을 주지 않는다고 덧붙인다. 기사는 그러나 이 "Anthropic이 개발한 것이 아니다"라는 문구가 핵심을 벗어난다고 지적한다. 공격자들은 별도의 가짜 extension을 만든 것이 아니라, Anthropic의 정품 extension ID인 `anthropic.claude-code` 아래에 version 2.1.313으로 배포했기 때문이다.

OpenSourceMalware의 공동 창업자 Jenn Gile은 이렇게 설명한다. 패키지는 스스로 `anthropic.claude-code` version 2.1.313이라고 밝히지만, 그 main JavaScript bundle 안에는 정품 extension 코드 앞에 삽입된 66줄짜리 악성 loader가 들어 있다는 것이다. 즉 사용자가 설치하는 파일은 정품 코드와 악성 코드가 한 덩어리로 섞인 형태이며, 정품 부분이 정상 동작하기 때문에 눈에 띄기 어렵다.

확산 범위에 대해서는, 악성 업데이트가 Cursor의 marketplace를 통해서만 배포되었고 Open VSX나 Microsoft의 공식 VS Code Marketplace에는 도달했다는 증거가 없다고 기사는 밝힌다. 그 두 채널을 통해 Claude Code를 설치한 사용자는 이번 사건의 영향을 받지 않은 것으로 알려졌다. 2026년 10월 30일 기준으로 악성 version은 제거되었고, Anthropic은 version 2.1.314를 Open VSX와 Microsoft VS Code Marketplace 양쪽에 게시했다.

악성 코드의 동작은 단계별로 서술된다. 먼저 VS Code가 시작되고 extension의 webview가 열리는 시점에 활성화된다. 다음으로 사용자의 `~/.ssh/authorized_keys` 파일에 공격자가 통제하는 키를 추가하는데, 이 키에는 `svc-telemetry`라는 이름표를 붙여 무해해 보이도록 위장한다. 그다음 피해자를 Windows, Linux, macOS 전반에서 SSH로 접근 가능한 상태로 만들려 시도하고, `134.209.82[.]225`로 reverse tunnel을 수립한다. 이어서 플랫폼별 지속성을 scheduled task, crontab, LaunchAgent 형태로 설치하고, 수집한 호스트 정찰 데이터를 암호화되지 않은 HTTP 요청으로 `134.209.82[.]225:8099/beacon`의 8099번 포트로 전송한다.

여기서 Cursor의 자체 분석이 중요한 단서를 제공한다. 로컬 SSH 서비스를 켜려면 관리자 권한이 필요한데, 악성 extension은 대부분의 macOS와 Windows 호스트에서 그 권한을 갖지 못한다는 것이다. 그런 호스트에서는 이 단계가 실패하므로 공격자가 tunnel을 통해 로그인할 수는 없었다. 그러나 Cursor는 그럼에도 불구하고 extension이 공격자의 SSH 키를 추가하고, 지속성을 설치하고, 호스트 세부 정보를 공격자에게 전송한다고 강조하며, 해당 호스트가 아니더라도 아래의 조치 지침을 따르라고 권고한다.

수집되는 데이터는 다음과 같이 열거된다. `api.ipify[.]org`에서 얻는 공인 IP 주소, 호스트명과 로컬 사용자명, 운영체제와 CPU 아키텍처, 홈 디렉터리와 현재 작업 디렉터리, `git config --global user.email`로 얻는 전역 Git 이메일, 그리고 KEY, TOKEN, SECRET, PASS, AWS, GCP 중 하나를 이름에 포함하는 최대 40개의 환경 변수 이름이다.

보안 연구자 Paul McCarty는 여기에 해석을 보탠다. 환경 변수의 "값"은 최초 beacon에 직접 담기지 않지만, 그 "이름"만으로도 어떤 클라우드 사업자와 CI 시스템, 어떤 종류의 자격증명이 설정되어 있는지가 드러난다는 것이다. 더 중요한 것은 SSH 접근이 성공할 경우 공격자가 해당 계정을 직접 들여다볼 수 있다는 점이다.

기사는 추가적인 후속 페이로드는 관찰되지 않았다고 전한다. 다만 reverse tunnel이 피해자의 SSH 서비스로 통하는 경로를 제공하므로, 공격자가 명령을 내리거나 파일을 전송할 수 있는 통로는 확보된 상태라고 설명한다. Gile의 발언도 인용된다. "매우 빠르게 내려갔지만, Claude Code instance를 auto-update로 설정해 둔 사람이라면 누구든 이 malware를 받아들였을 수 있다."

영향 규모와 시간창도 제시된다. Cursor는 2026년 10월 29일 태평양 시간 기준 오전 2시 27분경부터 오후 1시 35분경 사이에 악성 version을 설치한 최대 5,000명의 사용자가 영향을 받았다고 밝혔다. 회사는 영향받은 사용자에게 직접 연락하겠다고 했다. 해당 시간창에 오염된 extension을 설치한 사용자에게는 호스트 격리, 무단 SSH 키와 지속성 메커니즘 제거, 자격증명과 세션 교체가 권고된다.

기사는 이 사건을 단독 사례로 두지 않는다. 불과 일주일 조금 전, 신원 미상의 공격자가 OVHcloud의 공식 CLI인 `ovh/ovhcloud-cli`에서 이미 게시된 다섯 개 version의 release 바이너리를 비밀 탈취 malware로 교체한 사건이 있었다. 당시 악성 파일은 정당한 OVH 기여자의 GitHub 계정("HassenBF")을 통해 업로드되었는데, 그 계정은 2026년 3월 GlassWorm 작전의 일환으로 탈취된 상태였다. 정품 배포 경로와 정품 계정 신원이 그대로 악용된다는 점에서 두 사건의 구조가 같다.

끝으로 기사에는 정정 이력이 붙어 있다. 이전 판에서는 Open VSX 레지스트리의 extension이 침해되었다고 서술했으나, 사건은 Cursor VS Code Marketplace의 침해로 추적되었다는 것이다.

## 근거와 수치

- **최대 5,000명**: Cursor가 밝힌 영향 사용자 수다. 개발자 도구 하나의 사용자 기반에 비하면 작은 숫자로 보이지만, 이는 "그 시간창에 악성 version을 실제로 내려받은 사람"의 상한이다. 기사 자체가 Cursor의 발표를 인용한 자기 보고 수치이며, 독립적으로 검증된 값이 아니라는 점을 감안해야 한다.
- **version 2.1.313(악성) → 2.1.314(정품)**: 악성 version과 그다음 정품 version이 한 단계 차이다. 이는 공격자가 기존 version 번호 체계를 그대로 이어받아 "다음 업데이트"처럼 보이게 만들었고, 사고 수습도 번호를 하나 올리는 방식으로 이루어졌음을 보여 준다.
- **66줄짜리 loader**: 악성 코드의 분량이 66줄이라는 것은, 정품 bundle 전체를 다시 작성한 것이 아니라 앞부분에 짧은 코드를 끼워 넣는 방식이었다는 뜻이다. 삽입형 변조는 정품 코드의 기능을 유지하면서 탐지를 피하기 쉬운 전형적인 수법이다 (배경).
- **2026년 10월 29일 오전 2시 27분 ~ 오후 1시 35분(태평양 시간)**: 주어진 두 시각으로 계산하면 약 11시간 남짓의 노출 창이다. 악성 version이 하루가 안 되는 시간 동안 살아 있었다는 뜻이며, 동시에 야간에서 업무 시간으로 이어지는 구간이라 자동 갱신이 켜진 개발자 기기가 깨어 있는 시간대와 겹친다.
- **포트 8099, `134.209.82[.]225`**: 정찰 데이터를 보내는 목적지 주소와 포트다. 기사는 주소를 `134.209.82[.]225`처럼 대괄호로 흐트러뜨려 표기했는데, 이는 원문 PDF나 웹 문서에서 악성 주소가 자동으로 링크화되는 것을 막기 위한 관행이다 (배경).
- **암호화되지 않은 HTTP**: beacon이 HTTPS가 아니라 평문 HTTP로 나간다는 점은, 같은 네트워크에 있는 관찰자나 프록시 장비가 이 전송을 볼 수 있다는 뜻이다. 공격자 입장에서는 손실이지만, 탐지자 입장에서는 흔적이 남는다는 의미이기도 하다.
- **최대 40개의 환경 변수 이름**: 값이 아니라 이름만, 그것도 최대 40개다. 40이라는 상한은 수집 범위를 의도적으로 좁혀 전송 크기를 줄이고 눈에 덜 띄게 하려는 설계로 읽힌다.
- **`svc-telemetry`**: `~/.ssh/authorized_keys`에 추가되는 키에 붙는 이름표다. "telemetry(원격 측정)"라는 단어를 써서 정상적인 모니터링 구성 요소처럼 보이게 한 위장이다.
- **OVHcloud CLI의 다섯 개 version, 2026년 3월 계정 탈취**: 앞선 사례의 규모를 보여 주는 수치다. 이미 배포된 version을 사후에 교체했다는 점에서, 배포 후 불변성이 보장되지 않는 release 채널의 위험을 보여 준다.

## 따져볼 점

가장 큰 공백은 **침해 경로**다. 기사는 "공격자들이 권한 없는 업데이트를 밀어 넣은 정확한 방법은 불명확하다"고 두 번에 걸쳐 명시한다. publisher 계정 탈취였는지, marketplace 업로드 파이프라인의 결함이었는지, 내부자 관여였는지는 원문에 나오지 않는다. 이 지점이 밝혀지지 않으면 같은 경로로 재발할 가능성을 배제할 수 없다.

Cursor의 **"Anthropic이 개발한 것이 아니다"**라는 프레이밍도 비판 대상이다. 기사가 지적하듯, 사용자가 문제 삼을 것은 제작 주체가 아니라 "정품 ID와 정품 publisher 신원으로 악성 코드가 배포되었다"는 사실이다. 이 표현은 책임 소재를 제작사 쪽으로 밀어내는 효과를 낳는다. 다만 Cursor가 같은 성명에서 "SSH 서비스 활성화는 관리자 권한이 없어 실패했다"는 기술적 세부까지 자발적으로 공개한 점은 상대적으로 투명한 부분이다.

**"SSH 활성화 실패"라는 안심 포인트에도 한계가 있다.** 원문은 "대부분의 macOS와 Windows 호스트"라고 범위를 한정한다. Linux에서 관리자 권한이 확보된 환경이나, 사용자가 SSH 서버를 이미 켜 둔 개발자 장비에서는 이 단계가 성공할 수 있다는 여지가 남는다. 원문은 Linux에서의 성공 여부를 명시하지 않는다. 또 Cursor 자신이 인정하듯 SSH 키 추가, 지속성 설치, 정찰 데이터 전송은 실패 여부와 무관하게 실행되므로, "터널 로그인은 실패했다"가 "피해가 없었다"와 같지 않다.

**"최대 5,000명"은 발표 주체의 자기 집계다.** marketplace 로그를 기반으로 한 값으로 보이지만 산정 방법은 원문에 없다. 또한 이 수치는 설치자 수이고, 실제로 악성 코드가 실행되어 키가 추가된 호스트 수와는 다를 수 있다. 원문에는 실행 단계까지 도달한 호스트 수가 제시되지 않는다.

**환경 변수 처리에 대한 서술도 신중히 읽어야 한다.** McCarty는 "값은 최초 beacon에 직접 담기지 않는다"고 말했는데, 이는 값이 유출되지 않았다는 뜻이 아니라 이번 전송에 포함되지 않았다는 뜻이다. 원문은 후속 페이로드가 관찰되지 않았다고만 할 뿐, reverse tunnel이 열린 상태에서 추가 수집이 있었는지에는 답하지 않는다.

**표기상의 이상한 점**도 있다. 원문에는 Cursor를 "the SpaceXAI-owned company"로, Cursor의 다른 제품을 "our other SpaceXSI product"로 적는 대목이 있는데, 이런 관계에 대한 설명은 원문 어디에도 없다. 사실 관계를 확인할 수 없으므로 원문에 그렇게 적혀 있다는 것만 기록해 둔다. 아울러 기사 말미의 정정은 최초 보도가 Open VSX 침해라고 잘못 전했음을 인정한 것으로, 사고 초기의 채널 귀속이 얼마나 쉽게 어긋나는지를 보여 준다.

## 왜 중요한가

이 사건의 핵심은 악성코드의 기교가 아니라 **신뢰가 위임되는 지점**이다. 개발자는 `anthropic.claude-code`라는 식별자와 자동 업데이트를 신뢰하는데, 그 신뢰는 실제로 코드의 안전성이 아니라 publisher 계정과 배포 파이프라인의 무결성에 걸려 있다. 즉 extension marketplace는 개발자 머신에 대한 사실상의 원격 코드 실행 통로이고, 그 통로가 뚫리면 코드 편집기를 켜는 것만으로 감염된다. AI 코딩 도구가 개발자의 홈 디렉터리, Git 설정, 클라우드 자격증명과 같은 공간에 상주한다는 점을 감안하면, 이 통로의 가치는 다른 어떤 소프트웨어보다 높다.

실무적으로 당장 할 수 있는 일은 몇 가지다. 첫째, IDE extension의 자동 업데이트 정책을 점검하고 민감한 환경에서는 특정 version을 고정하는 방식을 검토할 만하다. 둘째, `~/.ssh/authorized_keys`와 crontab, LaunchAgent, Windows scheduled task를 주기적으로 훑어 모르는 항목이 없는지 확인하는 습관이 필요하다. 이 사건의 악성 키는 `svc-telemetry`처럼 그럴듯한 이름을 달고 들어왔으므로, 이름만 보고 판단하지 말고 키의 지문을 확인해야 한다. 셋째, 개발자 노트북에서 나가는 평문 HTTP beacon을 탐지할 수 있는 네트워크 가시성이 필요하다. 이번 사례는 HTTPS가 아니라 HTTP로 나갔기 때문에 잡아낼 기회가 있었다.

지켜볼 지점은 두 가지다. 하나는 Cursor와 Anthropic이 침해 경로를 언제, 얼마나 구체적으로 공개하는지다. 다른 하나는 marketplace 사업자들이 publisher 계정 보호(다중 인증, 서명된 배포, 배포 후 불변성)를 어느 수준까지 강제할 것인지다. OVHcloud CLI 사례에서 보았듯 이미 게시된 배포물을 사후에 바꿔치기할 수 있는 구조가 남아 있는 한, 이번과 같은 사고는 반복된다. 사용자 입장에서는 "어느 marketplace에서 받았는가"가 곧 위험도가 되는 시대이므로, 도구를 고를 때 배포 채널의 보안 모델도 함께 보아야 한다.
