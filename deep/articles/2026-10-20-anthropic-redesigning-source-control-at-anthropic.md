## 한 줄 요약

Anthropic 은 AI 코딩 에이전트가 하루 병합 코드 변경량을 2,500건에서 30,000건 이상으로 끌어올리자 Git 기반 monorepo 가 병목이 되었고, 클라이언트가 항상 온라인이라는 전제로 설계한 자체 버전 관리 시스템 Scion 을 5개월 만에 만들어 전사 monorepo 를 이전했으며 그 설계와 교훈을 공개했다.

## 배경과 핵심 개념

### Anthropic 과 Claude

Anthropic 은 대규모 언어 모델 기반 AI 비서인 Claude 를 만드는 회사이다. (배경) 이 글에서 Claude 는 단순한 코드 생성 도구가 아니라, 연구 루프를 자율적으로 반복하고 복잡한 프로그램을 미세 최적화하며 새로운 서비스를 처음부터 만드는 에이전트로 등장한다. Anthropic 은 다른 회사보다 훨씬 많이 Claude 를 내부 소프트웨어 개발에 사용하기 때문에, 사람 규모용 도구가 먼저 한계를 드러내는 지점을 가장 먼저 관찰한다고 주장한다. 또한 글 후반에는 Claude Mythos Preview 와 Claude Tag 라는 내부 릴리스가 Scion 구축을 가속했다고 언급된다.

### Monorepo

Monorepo 는 여러 프로젝트의 코드를 하나의 거대한 저장소에 모아 두는 방식이다. (배경) 장점은 변경을 한 번의 커밋으로 여러 구성 요소에 걸쳐 적용할 수 있고, 코드 재사용과 일관된 빌드가 쉬워진다는 점이다. 그러나 저장소 전체 크기와 변경 빈도가 커지면 clone, checkout, history 조회, CI 가 무거워진다. 이 글의 문제 상황은 Anthropic 의 monorepo 가 Git 으로 관리하기 어려울 만큼 빠르게 커졌다는 것이다.

### Git 의 분산형 설계

Git 은 모든 clone 이 완전한 저장소 사본이 되는 분산형 버전 관리 시스템이다. (배경) 오프라인에서도 diff 를 계산하고 history 와 blame 을 읽고 어떤 revision 이든 checkout 할 수 있다. 이 설계는 대부분의 저장소에 적합하고 Git 이 표준이 된 큰 이유다. 하지만 Anthropic 의 monorepo 처럼 history 만 100 GB 에 가깝고 작업 사본이 25 GB 를 넘는 경우, 완전한 사본을 유지하는 분산형 모델은 네트워크와 디스크 측면에서 매우 비효율적이 된다.

### Agent-scale 소프트웨어 개발

Agent-scale 은 사람이 코드를 쓰고 리뷰하는 속도가 아니라, AI 에이전트가 대량으로 코드를 생성하고 병합하는 부하를 기준으로 인프라를 설계해야 한다는 개념이다. 에이전트는 대부분 온라인이고, 로컬 저장소를 오래 유지하기보다 API 로 필요한 질문에 답을 받는 형태에 더 잘 맞는다. 이 글의 핵심 전제는 Git 이 사람의 오프라인 분산 작업을 위해 만든 특성이 에이전트 중심 작업에서는 오히려 확장을 방해한다는 것이다.

### Content-addressed storage 와 derived data

Content-addressed storage 는 데이터의 내용을 해시한 값을 주소로 사용해 같은 내용은 항상 같은 주소를 갖게 하는 저장 방식이다. (배경) 한번 저장된 데이터는 변하지 않으므로 여러 캐시 서버가 서로 확인하지 않고도 안전하게 캐시할 수 있다. Scion 은 변경 단위인 changeset 을 쓰고, blame 이나 path history 같은 질문에 빠르게 답하기 위해 changeset 으로부터 derived data 를 재귀적으로 계산한다. 이 구조는 데이터를 불필요하게 미리 만들지 않고 필요할 때 만들 수 있게 해 준다.

### 선행 사례

Google 의 Piper 와 Meta 의 Sapling, 특히 Sapling 의 서버 구성 요소인 Mononoke 는 거대한 monorepo 용 버전 관리 시스템의 선행 사례다. (배경) 이들은 Scion 이 사용하는 여러 기법, 특히 Bonsai 데이터 모델을 먼저 개척했다고 원문은 밝힌다. Anthropic 은 이들이 이미 얻은 교훈을 바탕으로 Scion 을 설계했다. 따라서 Scion 은 완전히 새로운 발명이라기보다, 기존 대규모 시스템의 아이디어를 AI 에이전트 시대의 부하에 맞게 재조합한 사례다.

## 글의 내용

### 문제 인식과 Scion 의 등장

글은 먼저 Anthropic 에서 코딩 자체가 더 이상 시스템 구축이나 연구의 병목이 아니라고 진단한다. Claude 가 자율적으로 연구 루프를 돌리고 복잡한 프로그램을 최적화하고 새 서비스를 빠르게 만들 수 있게 되면서, 병목은 사람 규모용 개발자 인프라로 옮겨 갔다. 구체적으로 2026년 5월에는 하루 약 2,500건의 코드 변경이 병합되었고, 9월에는 하루 30,000건 이상으로 늘었다. 원문은 코드 병합에 대한 잠재 수요가 사실상 무한하며 병목을 제거할 때마다 생산량이 다시 늘어난다고 말한다.

이 부하를 감당하기 위해 Anthropic 은 자체 버전 관리 시스템인 Scion 을 만들었고, 5개월 만에 monorepo 를 Git 에서 Scion 으로 완전히 이전했다. 같은 기간에 Antique 라는 코드 리뷰 시스템, 코드 검색, 소스 컨트롤용 IAM, 대량의 리뷰된 코드를 안전하게 병합하는 도구도 함께 만들었다. 글은 Scion 에 초점을 맞춘다. Claude 가 코드를 대량으로 쓰는 능력이 문제를 만들었지만 동시에 그 문제를 해결할 시스템을 빠르게 만드는 데도 쓰였다는 점이 흥미로운 사례라고 설명한다.

### 왜 Git 이 한계에 부딪혔는가

원문은 Anthropic 의 작업 부하가 얼마나 특이한지 먼저 설명한다. Anthropic 은 거의 모든 다른 회사보다 Claude 를 소프트웨어 작성에 훨씬 많이 사용하므로, 사람 규모용 도구가 strain 을 일으키는 지점을 먼저 본다. Git 은 분산형 시스템이고 모든 clone 이 완전한 저장소 사본이다. 대부분의 저장소에는 이 설계가 옳지만 Anthropic 의 monorepo 는 점점 그 설계 공간에서 벗어난다.

구체적으로 main branch 의 history 만 거의 100 GB 이고 압축된 작업 사본은 25 GB 를 넘는다. CI 를 위해 하루 약 2,500만 회의 코드 checkout 을 수행하는데, 이를 순진하게 전체 fetch 하면 하루 600 PB 이상의 Git 트래픽이 발생한다고 계산한다. Git 은 shallow clone, sparse checkout, promisor remote 같은 부분 저장소 도구를 제공한다. 그 너머에는 내부 Git mirror 와 blob storage 에 저장된 snapshot 이라는 표준 우회책이 있다. Anthropic 은 이 모든 것을 사용했고, 최고조에는 부하를 처리하기 위해 수백 개의 내부 Git mirror 를 운영했다. 하지만 병합 속도가 빨라지면서 mirror 운영이 어려워졌고, snapshot 은 갱신 사이에 main 의 최신 상태에서 점점 멀어졌다. diff 와 blame 처럼 history 에 의존하는 작업을 partial clone 위에서 유지하는 데 점점 더 많은 주의가 필요해졌다.

그다음 원문은 중요한 관찰을 제시한다. 대부분 회사와 마찬가지로 Anthropic 도 Git 을 하나의 권위 있는 사본이 있는 중앙 집중형 시스템처럼 쓰고 있었지만, 클라이언트는 거의 모두 온라인인 에이전트와 job 이었다. Git 의 오프라인 분산 작업 특성이 오히려 확장을 방해하고 있었다. 그래서 “에이전트가 항상 온라인이라는 사실을 처음부터 염두에 두고 소스 컨트롤을 설계하면 어떻게 될까”라는 질문을 던진다.

### Scion 의 설계 원칙

Scion 은 거대한 monorepo 용 소스 컨트롤의 선행 사례인 Google Piper 와 Meta Sapling 의 교훈을 반영했다. 원문은 여섯 가지 원칙을 제시한다.

첫째, 클라이언트는 항상 온라인이다. Git 은 클라이언트가 오프라인에서 작업하고 저장소 전체 사본이 필요하다고 가정하지만, Scion 은 거의 모든 클라이언트가 에이전트와 job 이므로 항상 도달 가능한 서버를 중심으로 설계했다. 클라이언트는 필요할 때 데이터를 가져온다.

둘째, 클라이언트와 서버의 비대칭이다. Git 에서는 모든 클라이언트가 서버가 될 수 있지만 Scion 에서는 서버가 파일 history, blame, commit 생성, merge, rebase 같은 질문과 작업을 처리한다. 클라이언트는 제한된 로컬 객체 캐시를 유지하고 작업 사본 파일을 디스크에 배치하며 파일 시스템 변경을 감시하고 서버와 편하게 작업할 수 있는 인터페이스를 제공한다. 클라이언트는 스스로 계산할 수 있는 것이 거의 없지만 그 대가로 로컬 데이터가 훨씬 적게 필요하다.

셋째, 포괄적인 소스 컨트롤 서비스는 여러 새로운 애플리케이션을 가능하게 한다. Git 에서는 어떤 줄을 누가 마지막으로 바꿨는지, 두 커밋이 어떤 관계인지 같은 질문을 하려면 로컬 저장소 사본을 유지하거나 벤더별 API 에 의존해야 한다. Scion 은 클라이언트가 쓰는 모든 소스 컨트롤 질의를 API 로도 제공하므로 많은 job 이 로컬 저장소 없이도 동작할 수 있다. 자동 bisect 나 revert pipeline 같은 내부 도구는 이 값싼 프로그램 방식 접근이 없으면 규모에서 실용적이지 않다고 원문은 말한다.

넷째, 모든 것이 수평 확장 가능해야 한다. Git mirror 수백 개를 운영할 때 저장소가 mirror 의 디스크나 메모리 한계를 넘어서면 확장이 막혔다. Scion 에서는 저장소 데이터가 분산되고 각 구성 요소가 독립적으로 확장 가능하다. 서버를 포함해 어디에도 완전히 materialize 된 저장소 사본이 없다. Git 의 packfile 같은 압축 객체 묶음이 없으므로 저장소 유지 보수도 필요 없다.

다섯째, commit 은 저렴하고 점진적이며 lock-free 여야 한다. Git 에서는 로컬에서 commit 하고 push 해야 하지만 Scion 에서는 모든 commit, rebase, merge 가 서버에서 일어나므로 push 할 것이 없다. 대신 각 작업이 빨라야 한다. commit 생성 비용과 그에 따른 downstream 데이터 구조 갱신 비용은 변경 크기에 비례해야 하며 저장소 전체 크기에 비례하면 서버가 따라갈 수 없다. Scion 의 개발 수명 주기는 main ref 나 release branch 를 제외하고 ref 를 사용하지 않도록 권장하는데, 모든 서버가 동의해야 하는 전역 상태는 확장 문제를 일으키기 때문이다.

여섯째, 작업 사본은 선택 사항이고 기본적으로 sparse 하다. monorepo 가 너무 크고 CI 를 위해 하루 수천만 번 checkout 을 하므로 가능하면 checkout 을 피하고 싶었다. 예를 들어 어떤 commit 과 merge base 사이의 diff 가 필요한 CI job 은 서버에 요청하면 된다. 쓰기 작업도 많은 경우 checkout 없이 API 만으로 처리할 수 있다. Scion 의 프로토콜은 클라이언트가 요청한 디렉터리만 포함하는 sparse checkout 과 파일을 요구할 때만 materialize 하는 virtualized checkout 을 중심으로 한다. 그래서 job 이 실제로 디스크에서 파일이 필요할 때만 읽은 만큼 비용을 지불한다.

### Scion 의 데이터 구조

Scion 의 작업 단위는 changeset 이고, 이는 write-ahead log 의 항목이다. changeset 은 Git 의 commit 이 저장하는 대부분의 정보를 저장한다. Git commit 이 tree 를 가리키는 포인터를 저장하는 것과 달리, changeset 은 첫 번째 parent 대비 변경된 파일 목록과 blob storage 의 압축 파일 내용을 가리키는 content-addressed pointer 를 저장한다. changeset 은 서버 쪽에서 생성되고 즉시 모든 곳에서 사용할 수 있다.

이 구조는 packfile 을 받을 필요가 없고 locking 이나 서버 간 coordination 이 없으며 옮길 ref 도 없기 때문에 매우 높은 처리량으로 changeset 을 받아들일 수 있게 해 준다. Scion 은 기술적으로 ref 를 지원하지만 commit 생성이나 fetch 에 ref 가 필요 없으므로, ref 를 옮기는 것은 Spanner 의 단일 row 에 대한 compare-and-swap 으로 changeset 생성과 분리되어 일어난다.

changeset 은 변경된 내용만 기록하므로 그 자체로는 어떤 줄을 누가 마지막으로 편집했는지, 어떤 commit 이 파일에 영향을 주었는지 같은 질문에 빠르게 답할 수 없다. 이 질문에 답하기 위해 Scion 은 changeset 으로부터 추가 데이터 구조를 만든다. 여기에는 파일 blame, path history 전용 구조, commit graph 용 skip list 가 포함된다. changeset 에 직접 속하지 않는 모든 것을 derived data 라고 부르며, 하나의 일반적인 메커니즘으로 계산한다. 각 derived data 유형은 재귀적으로 정의되어, 어떤 changeset 에 대한 값은 그 changeset 의 parent 들에 대한 값에서 계산된다.

이 메커니즘은 세 가지 이점을 준다. 첫째, 어떤 작업을 빠르게 만드는 새 데이터 구조가 필요하면 derived data 유형을 쉽게 추가할 수 있다. 둘째, 유형마다 eager 하게 계산할지 defer 할지 선택할 수 있어 불필요한 데이터를 materialize 하지 않는다. 셋째, 클라이언트가 이 데이터 구조의 내부를 보지 않으므로 클라이언트를 바꾸지 않고 내부 구현을 최적화할 수 있다. 실제로 시스템이 커지면서 copy detection 이나 path 기반 파일 검색을 위한 새 index 같은 derived data 유형이 여러 번 추가되었다.

### Scion 의 확장 구조

Scion 서버의 소규모 fleet 은 클라이언트에 필요한 모든 소스 컨트롤 API 를 제공한다. changeset 가져오기, diff 계산, merge base 찾기, blob fetch 등이 여기에 해당한다. 모든 소스 컨트롤 데이터는 content-addressed 이므로 한번 저장되면 변하지 않고, 어떤 서버든 다른 서버와 확인하지 않고 캐시할 수 있다. 따라서 서버들은 수평 확장 가능하고 coordination 이 거의 필요 없다. 서버는 본질적으로 큰 캐시이며, 그 자리에서 derived data 를 계산하고 결과를 Spanner 에 다시 쓸 수도 있다.

Scion 을 쓰는 많은 consumer 는 더 이상 자체 로컬 저장소를 유지할 필요가 없다. 예전에는 commit ancestry 나 blame 같은 질문이 필요한 CI job 이나 도구가 저장소를 fetch 하고 유지하는 것이 큰 부담이었다. 이전 초기에는 자체 클라이언트, repo format, 프로토콜이 있기 전에 Scion 이 이런 metadata 질의만 처리했다. 파일 내용을 가져오고 작업 사본을 materialize 하는 것은 훨씬 데이터 집약적이라 별도 설계가 필요했다.

Scion 의 scn 클라이언트는 Git 의 fetch 프로토콜과 몇 가지 중요한 차이가 있다. 우선 negotiation 이 클라이언트가 이미 가진 것을 서버에 알려 주지 않는다. 대신 클라이언트가 원하는 tree 와 blob 에 대해서만 동작한다. root tree 에서 시작해 클라이언트는 로컬 저장소에서 없는 tree 를 확인하고 재귀적으로 요청한 다음, blob 에 대해 같은 과정을 반복한다. 모든 요청은 변하지 않는 특정 객체에 대한 것이므로 어떤 캐시든 응답할 수 있고, 이 구조는 전통적인 tiered cache 와 비슷하다. multi-gigabyte packfile 응답이 없으므로 효율적이고 재개 가능하다. sparse checkout 이나 virtualized checkout 도 특별한 지원이 필요 없다. 클라이언트가 원하지 않는 tree 를 요청하지 않으면 되기 때문이다.

fleet 안에서 클라이언트는 socket 을 통해 scion-daemon 과 통신하고, scion-daemon 은 노드 전체의 객체를 저장한다. 대부분의 노드가 monorepo 접근이 필요하고 같은 노드의 job 들은 대부분 같은 객체를 재사용한다. 각 daemon 은 주기적으로 갱신되는 snapshot 에서 시작하고, 같은 region 의 tree 와 blob 캐시 서버인 scion-cache 에만 요청한다. 이 캐시 서버는 객체를 메모리에서 직접, daemon 이 소비할 디스크 포맷 그대로 스트리밍하므로 클라이언트의 missing object 를 계산하거나 delta compression 을 수행하는 데 시간을 쓰지 않는다. 캐시에 객체가 없으면 권위 있는 scion-server 에 요청하고, scion-server 는 필요에 따라 Spanner 나 cloud storage 에서 읽는다.

scion-daemon, scion-cache, scion-server 는 이 프로토콜에 대해 동일한 RPC 로 응답하므로 클라이언트는 캐시 topology 를 알 필요가 없다. 이론적으로 어떤 tier 든 다른 tier 와 통신할 수 있지만, failure domain 을 격리하기 위해 tiering 을 엄격하게 강제한다. region scion-cache 의 장애가 upstream scion-server 를 압도해 전체 시스템이 죽는 상황을 막으려는 것이다.

각 tier 는 99% 이상의 cache hit rate 를 유지하고 오래 살아 있는 상태가 필요 없어 확장하기 쉽다. Scion 인프라 footprint 는 이전 Git mirror 인프라보다 CPU 와 메모리 요구량 기준으로 200배 작다. CI 와 research job 의 checkout 은 두 자릿수 배 빠르며, 분 단위에서 초 단위로 줄었다. CI 만으로 25% 의 CPU 용량을 확보했다. 클라이언트나 캐시 모두 repository maintenance 를 수행할 필요가 없어 job 수명 주기 관리도 단순해졌다.

### Scion 을 만들면서 배운 것

Scion 구축은 Claude Mythos Preview 와 Claude Tag 가 내부적으로 사용 가능해진 시기와 비슷하게 시작되었다. 이 두 릴리스는 Scion 의 필요성을 동시에 증폭시켰고 구축 속도도 크게 높였다. 특히 초기에 손으로 쓴 Git-to-Scion ingestion pipeline 프로토타입을 Claude Mythos Preview 초기 내부 snapshot 에 다시 쓰게 했더니, 추가 지시 없이도 ingestion ordering 과 데이터 구조에 관한 암묵적 invariant 를 모두 유지하면서 메모리 사용량이 20배 적고 4배 빠른 버전을 만들었다고 한다.

원문은 이 프로젝트에서 얻은 교훈을 몇 가지로 정리한다.

첫째, 소규모 팀의 빠른 개발이 더 흔해질 것이다. Scion 과 Antique, 그리고 관련 시스템 여섯 개 이상을 7명 팀이 만들고 5개월 만에 완전히 이전했다. 같은 기간 하루 병합 코드량은 10배 늘었다. 과거에는 이런 소스 컨트롤 시스템을 개발하고 배포하는 데 수년과 훨씬 많은 엔지니어가 필요했을 것이라고 원문은 말한다.

둘째, 엔지니어의 가치가 줄어든 것이 아니라 일의 성격이 변하고 있다. 이 시스템을 만든 엔지니어들은 모두 Claude 가 자신보다 코드를 잘 쓴다고 평가한다고 한다. 하지만 엔지니어는 상위 수준의 시스템 간 구성 요소 이해, 설계 수준의 tradeoff 판단, 해결할 문제와 달성해야 할 규모에 대한 선택을 계속 공급했다. 자주 엔지니어의 역할은 Claude 에게 “아니요”라고 말하는 것이었다. 에이전트는 시스템의 핵심 제약을 어기고 허용되지 말아야 할 패턴을 만족시키려 하기도 한다. 예를 들어 migration 중에 어떤 변경이 main 에 병합된 시점을 알아내기 위해 커밋 로그를 선형으로 읽는 brute force 방식을 시도한 시스템이 여러 개 있었다. Anthropic 은 adversarial review 도 광범위하게 사용하는데, 이는 매우 효과적이지만 근시안적일 수 있어 숙련된 엔지니어가 가상의 우려에 반응한 과도한 엔지니어링을 막아야 했다. 한 리뷰는 다른 내부 서비스를 과도하게 불신해 Claude 가 과도한 validation 과 복잡성을 추가하게 만든 사례도 있었다. 팀은 여전히 모든 변경 요청을 리뷰하지만, 이제는 모든 코드 줄을 읽기보다 변경의 의도를 검토한다.

셋째, 최적화와 품질을 상당히 개선할 수 있었다. Claude 가 엄청난 양의 코드를 빠르게 쓸 수 있기 때문에 Scion 은 팀이 지금까지 작업한 코드베이스 중 가장 테스트가 잘 되어 있고 방어가 잘 되어 있는 축에 속한다. 빠듯한 일정에도 불구하고 겪은 모든 비자명한 인프라 및 소스 컨트롤 상호작용에 대한 hermetic simulation, fuzzing, 정교한 rate limiting 을 만들 수 있었다. Claude 는 인덱스 하나를 놓친 ancestry query 의 알고리즘 최적화 같은 중요한 최적화도 우연히 찾아냈는데, 이는 전문가가 며칠에서 몇 주 분석하고 튜닝할 일이었다고 원문은 전한다.

넷째, 새로운 형태의 monorepo 보안 기반을 마련했다. 거대한 monorepo 에서 safety, security, compliance 를 관리하는 것은 크기와 규모 관리만큼 중요하다. Scion 은 저장소에 대한 풍부한 접근 제어를 지원하고 개별 디렉터리에 권한을 적용해 가장 민감한 코드를 보호하면서 monorepo 의 이점을 잃지 않게 한다. 또한 코드 리뷰 도구는 승인에 복잡한 semantic constraint 를 표현할 수 있어, comment-only 변경과 민감한 logical 변경을 구분해 인간 리뷰어가 가장 중요한 변경에 집중하게 한다.

다섯째, 새로운 수준의 operational excellence 가 가능하다. 팀은 Claude Tag 를 많이 사용해 각 구성 요소를 모니터링했다. 예를 들어 Slack 채널마다 하나의 구성 요소 상태에 집착하도록 Claude 를 설정했고, 이들을 superfan 이라고 부른다. scion-daemon superfan, scion-cache superfan, Antique merge queue superfan 등이 있다. 이들은 telemetry 와 log 에 접근할 수 있고, 차트를 새로고침하며 이상한 것을 찾는 것 외에는 할 일이 없는 숙련된 엔지니어처럼 행동한다. 전통적인 alert 도 있지만 superfan 은 그 alert 이 일차원적으로 보일 만큼 미묘하고 새로운 문제를 감지할 수 있다고 한다.

여섯째, 기존의 사전 가정을 완전히 재검토하게 되었다. 이 프로젝트는 사람 규모용으로 설계된 다른 워크플로를 다시 보게 만들었다. 예를 들어 merge queue 는 agent scale 에서 큰 의미가 없다. 테스트가 실행되는 동안 수백 또는 수천 개의 변경이 병합될 수 있는데 CI 가 무슨 의미인가 하는 질문이 생긴다. 업계 표준인 merge queue 의 전역 repository lock 을 효과적으로 재현하지 못했기 때문에, 대신 post-merge 및 pre-deploy 자동 테스트에 투자했다. 동시 변경이 충돌할 수 있지만 Claude 는 사람이 충돌을 식별하는 것보다 더 빨리 고칠 수 있다고 말한다.

### 생태계에 대한 기여

원문은 Scion 이 점점 더 유능한 AI 에이전트가 제기하는 확장 문제에 대한 답의 일부일 뿐이라고 본다. 이 내용을 비슷한 문제를 해결하려는 팀을 위한 사례로 공유하지만, 이 해법이 모든 경우에 맞을 것이라고 기대하지는 않는다. Scion 은 일반적인 용도로 Git 을 대체할 만한 것이 아니다. 여기서 설명한 개념은 정말 거대한 monorepo, 즉 수만 명의 엔지니어가 있거나 에이전트 떼가 엄청난 코드를 쓰는 경우에만 의미가 있다. 게다가 Anthropic 은 내부 사용을 위해 토큰을 쓸 수 있는 능력이 다른 사업체가 현실적으로 쓰고 싶은 수준을 훨씬 넘는 독특한 회사라고 인정한다.

실용적으로 보면 Scion 을 다른 조직에 널리 유용한 형태로 제공하기는 어렵다. Git 과 크게 갈라져서 개발 수명 주기의 모든 부분을 이전해야 하고, 자체 코드 리뷰, 코드 검색, CI 가 필요하다. 내부 버전은 매우 bespoke 하여 다른 조직이 도입하기 어렵고, 모두를 만족시키려는 공개 버전을 만들면 실제로는 별로 유용하지 않을 것이라고 우려한다.

하지만 원문은 이런 문제 부류가 앞으로 6개월에서 12개월 사이에 더 흔해질 것으로 예상한다. 모든 Git 사용 회사가 비슷한 문제를 각자 해결하는 것은 엔지니어링 자원의 비효율적 사용이므로, 가장 영향력 있는 일은 사고를 공유해 다른 개발자가 Git 모델 전체를 떠나지 않고 Scion 의 성공적인 부분 일부를 적용할 수 있게 하는 것이라고 말한다. Git 서버가 Git 클라이언트와 똑같이 동작할 필요는 없다. 상당한 확장 개선을 주는 새로운 서버 아키텍처가 존재하며, Git 플랫폼은 Scion 같은 포괄적인 server-side RPC 를 제공할 수 있고, 여러 forge 간에 표준화해 Git 클라이언트가 배울 수 있게 할 수도 있다. negotiation protocol 도 오늘과 똑같을 필요가 없고, Git 의 sparse 와 shallow 기능도 서로 잘 조합되게 만들 수 있다.

마지막으로 원문은 Git 커뮤니티가 거의 20년 동안 수백만 개발자를 위해 플랫폼을 확장해 왔다는 점을 인정한다. Anthropic 의 기여는 훨씬 좁은 범위로, agentic 소프트웨어 개발이 이 시스템들과 어떻게 상호작용하는지에 대한 초기 관점을 공유하고 GitHub, GitLab, OSS 커뮤니티와 협력해 개발자의 변화하는 요구를 지원하려는 것이다.

## 근거와 수치

원문은 여러 구체적인 수치를 제시한다. 2026년 5월 하루 병합 코드 변경량은 약 2,500건이었고, 9월에는 하루 30,000건 이상이었다. 이는 약 4개월 만에 12배 성장한 것으로, 원문은 이 속도가 당분간 느려지지 않을 것으로 본다. 하루 30,000건은 사람이 직접 리뷰하고 병합하기에는 매우 큰 수치이며, Git 기반 전통 CI 와 코드 리뷰 파이프라인이 처리하기 어려운 규모다.

monorepo 의 main branch history 만 거의 100 GB 이고 압축된 작업 사본은 25 GB 를 넘는다. 일반적인 개발자 노트북이나 CI 컨테이너가 전체 clone 을 유지하기 어려운 크기다. CI 를 위해 하루 2,500만 회의 checkout 을 수행한다는 수치는 개발자 환경, 에이전트 sandbox, 연구 job 을 제외한 것이다. 이를 순진하게 전체 fetch 하면 하루 600 PB 이상의 트래픽이 발생한다는 계산은 대규모 데이터센터 수준에서도 감당하기 어려운 양이다.

Git 우회책으로 최고조에 수백 개의 내부 Git mirror 를 운영했다는 사실은 Git 기본 구조만으로는 부하를 흡수하지 못했다는 증거다. 그런데도 mirror 의 디스크나 메모리 한계 때문에 확장이 막혔다고 한다.

Scion 구축에는 7명의 팀이 참여했고, Scion 과 Antique 및 관련 시스템 여섯 개 이상을 만들고 5개월 만에 전사 monorepo 를 이전했다. 같은 기간 하루 병합 코드량이 10배 증가했다. 소스 컨트롤 시스템 교체치고는 매우 짧은 기간이고 팀 규모도 작다. 원문은 과거 같으면 수년과 훨씬 많은 엔지니어가 필요했을 것이라고 해석한다.

Claude Mythos Preview 가 손으로 쓴 ingestion pipeline 을 다시 써서 메모리 사용량 20배 감소, 속도 4배 향상을 달성했다는 사례는 AI 가 단순 반복 작업이 아니라 복잡한 시스템 컴포넌트 재작성에서도 큰 폭의 최적화를 낼 수 있음을 보여 준다.

Scion 인프라 footprint 는 이전 Git mirror 인프라 대비 CPU 와 메모리 요구량이 200배 작다. checkout 은 두 자릿수 배 빨라져 분 단위에서 초 단위로 단축되었다. CI 에서만 25% 의 CPU 용량을 확보했다. 이는 단순히 코드 저장소를 바꾼 것이 아니라 전체 fleet 의 컴퓨팅 효율에 큰 영향을 주었다는 의미다. 각 tier 의 cache hit rate 는 99% 이상이다. 99% 라는 수치는 반복적으로 같은 코드를 읽는 CI 와 에이전트 작업에서 캐시가 매우 효과적임을 보여 준다.

원문에 나온 6개월에서 12개월 후 문제가 더 흔해질 것이라는 예측은 계측된 수치가 아니라 저자의 전망이다. Scion 의 성능 개선 차트도 원문에 이미지로 존재하지만 정확한 축 수치는 본문 텍스트에 명시되어 있지 않다.

## 따져볼 점

이 글은 Anthropic 이 자사 제품인 Claude 의 성능과 자체 인프라 성과를 소개하는 성격이 강하다. Scion 의 성능 개선, Claude 가 ingestion pipeline 을 20배 메모리 절감과 4배 속도 향상으로 재작성했다는 주장, 7명 팀의 5개월 이전 성공담은 모두 내부 측정치이며 외부 독립 검증이나 벤치마크가 제시되지 않았다. Anthropic 은 Claude 를 판매하는 회사이므로 “Claude 가 문제를 만들었고 Claude 가 해결했다”는 서사는 자사 제품 홍보와 이해관계가 얽혀 있다.

원문 스스로도 Scion 이 일반적인 Git 대체재가 아니라고 인정한다. 이 설계는 수만 명 엔지니어나 대규모 에이전트를 가진 거대한 monorepo 에만 의미가 있고, Anthropic 은 내부 토큰 사용량이 다른 사업체보다 훨씬 많은 독특한 환경이다. 또한 Scion 은 Git 과 크게 달라 코드 리뷰, 코드 검색, CI 를 모두 맞춤형으로 이전해야 하며, 공개형으로 만들면 유용하지 않을 것이라고 밝힌다. 따라서 독자가 이 글을 보고 곧바로 Scion 을 도입할 수 있다고 기대해서는 안 된다.

기술적으로 몇 가지 빠진 정보가 있다. Scion 이 의존하는 Spanner 의 정확한 스키마, cloud storage 비용, latency 분포, 장애 발생 시 복구 시간, 데이터 일관성 보장 범위는 자세히 나오지 않는다. “어디에도 완전히 materialize 된 저장소 사본이 없다”는 설계는 중앙 집중형 시스템의 가용성과 내구성 tradeoff 를 수반할 수 있는데, 이에 대한 실패 사례나 한계는 다루지 않는다. lock-free commit 과 ref 를 줄이는 설계는 동시 변경이 많을 때 충돌을 늦게 발견하게 만들 수 있다. 원문은 global repository lock 을 재현하지 못해 post-merge 및 pre-deploy 테스트에 투자했고, 동시 변경 충돌이 생길 수 있다고 인정한다. 이는 Claude 가 충돌을 빨리 고친다고 하지만, 그런 자동화 능력이 없는 조직에는 위험한 tradeoff 일 수 있다.

“클라이언트는 항상 온라인”이라는 전제도 명시적인 한계다. 오프라인 분산 개발, 네트워크 단절, 임시 로컬 실험, 외부 협력자 기여 같은 Git 의 장점을 포기한 설계다. Anthropic 의 내부 에이전트와 job 환경에는 맞을 수 있지만 일반 소프트웨어 개발에는 맞지 않는다.

AI 기반 운영 superfan 이 전통 alert 보다 미묘한 문제를 잘 감지한다는 주장도 정량적 오탐률이나 놓친 사고 사례 없이 제시된다. 코드 리뷰에서 “모든 줄을 읽지 않고 의도만 검토”하는 방식은 속도에는 유리하지만, 자동화된 리뷰가 놓칠 수 있는 보안 취약점이나 논리 오류가 완전히 걸러진다는 근거는 없다. agentic 코드의 품질과 보안에 대한 장기적 평가는 원문에 없다.

마지막으로 “6개월에서 12개월 안에 이 부류의 문제가 더 흔해질 것”이라는 전망은 근거 데이터가 아니라 저자의 기대다. AI 코딩 도구 사용 기업 모두가 Anthropic 과 같은 병목에 도달할지는 산업별 코드베이스 크기, 에이전트 사용 강도, 클라우드 비용 구조에 따라 달라질 수 있다.

## 왜 중요한가

이 글은 AI 코딩 에이전트가 일상화되면 Git, CI, 코드 리뷰 같은 개발자 인프라가 새로운 병목이 될 수 있다는 신호를 구체적 수치와 함께 보여 준다. 실무자는 자신이 관리하는 저장소의 병합 빈도, checkout 횟수, monorepo 크기, CI 대기 시간을 먼저 측정해 보는 것이 좋다. 하루 수천 건 이상의 병합이 예상된다면 Git 의 표준 clone-push-review 흐름이 어디서 먼저 막힐지 미리 점검할 필요가 있다.

Scion 의 아이디어 중 상당수는 Git 을 떠나지 않고도 적용할 수 있다. Git 호스팅 플랫폼이 더 풍부한 server-side RPC 를 제공하면 CI job 이 로컬 저장소를 유지하지 않고 diff, blame, merge base 같은 질문을 API 로 처리할 수 있다. sparse checkout 과 virtualized checkout 을 조합하면 대규모 monorepo 에서 실제로 읽는 파일만 materialize 하도록 만들 수 있다. content-addressed 캐시 계층과 지역 캐시 서버 구조는 기존 Git mirror 보다 훨씬 적은 자원으로 checkout 부하를 흡수할 수 있는 설계 참고가 된다.

또한 이 글은 AI 시대의 엔지니어링 팀 운영에 대한 실용적 단서를 준다. 7명 팀이 대형 인프라를 5개월 만에 이전했다는 사례는 AI 지원 개발이 팀 규모와 일정에 대한 기존 가정을 바꿀 수 있음을 보여 준다. 그러나 동시에 엔지니어의 역할은 단순 코딩이 아니라 시스템 설계, tradeoff 판단, 과도한 자동화나 과잉 방어를 막는 판단으로 이동한다. 실무자는 “AI 가 코드를 더 빨리 쓰게 하는 것”보다 “AI 가 만든 변경의 의도와 제약 조건을 검토하는 것”에 리뷰 프로세스를 다시 설계할 필요가 있다.

운영 측면에서 superfan 같은 AI 모니터링 패턴은 전통 alert 이 놓치는 이상 징후를 찾는 보조 수단으로 실험해 볼 만하다. 다만 환각이나 과잉 대응을 막기 위해 사람이 최종 판단하는 경로를 남겨 두는 것이 중요하다.

마지막으로 이 글은 merge queue 와 CI 의 의미가 고정된 것이 아니라 개발 속도에 따라 다시 정의되어야 함을 시사한다. 수백 또는 수천 개 변경이 동시에 병합되는 환경에서는 사전 global lock 보다 post-merge 및 pre-deploy 테스트가 더 현실적일 수 있다. 소프트웨어 조직은 자신의 병합 동시성과 테스트 비용을 기준으로 이런 tradeoff 를 검토하고, GitHub, GitLab, OSS 커뮤니티가 Scion 의 성공적인 부분을 표준 Git 생태계에 어떻게 흡수하는지 지켜보는 것이 좋다.
