## 한 줄 요약

이 논문은 에이전트를 감싸는 제품별 runtime harness가 결정하는 실행 규칙, 즉 어떤 행동이 지금 실행 가능하고 어떤 의무가 남아 있으며 언제 끝낼 수 있는지를, 기존의 행동 모방 방식처럼 암묵적으로 남겨두지 않고 control document라는 명시적 지도 신호로 바꾸어 학습시키는 Harness Policy Distillation 기법을 제안한다.

## 핵심 개념 풀이

### 1. runtime harness

runtime harness는 언어 모델이 실제 에이전트로 배포될 때 그 바깥을 감싸는 제품별 실행 환경이다. 이 단어의 원래 뜻은 말에 채우는 마구인데, 모델이 마음대로 행동을 출력해도 실제로 어떤 행동이 허용되는지, 그 행동이 어떤 상태 변화를 일으키는지, 그리고 언제 작업이 끝나는지를 이 harness가 통제한다는 점에서 그런 비유가 붙었다. 구체적으로 harness는 사용자에게 보이는 대화 이력을 직렬화하고, 실행 가능한 도구 인터페이스를 노출하며, 권한 검사와 워크플로 단계를 관리하고, 도구 실행 결과를 관찰로 삽입하며, 다음 모델 호출을 예약하고, 유효한 종료 조건을 정의한다. 예를 들어 똑같은 모델이라도 한 제품의 harness에서는 "먼저 조회를 한 뒤에만 최종 답변을 할 수 있다"는 규칙을 강제할 수 있고, 다른 제품의 harness에서는 그 순서가 다르거나 종료 권한이 다를 수 있다. 따라서 일반 모델이 특정 제품 안에서 제대로 동작하는 에이전트가 되려면, 단순히 도구 사용법을 아는 것이 아니라 바로 그 harness의 실행 계약을 따르는 정책을 배워야 한다.

### 2. runtime semantics와 runtime control state

runtime semantics는 특정 시점에 그 harness가 무엇을 요구하고 무엇을 허용하는지에 대한 실행 의미론이다. 같은 관측 이력이 주어져도 "이 도구가 지금 사용 가능하다"는 사실만으로는 그 도구 호출 의무가 이미 완료되었는지, 아니면 아직 대기 중인지 알 수 없다. runtime control state는 이러한 실행 제어 상태를 담는 개념으로, 남아 있는 obligation, 지금 호출 가능한 ready call들, 현재 lifecycle 단계, final response를 내도 되는지 여부 같은 것들을 포함한다. 일반적인 trajectory 데이터에는 모델이 어떤 행동을 했는지(action label)는 기록되어 있지만, 그 행동 직전에 어떤 runtime control state였는지는 명시되어 있지 않다. 이게 암묵적이면 학습 중에는 단순히 "이 history에서는 이 action이 나왔다"만 맞추게 되고, 왜 그 action이 지금 유효한지에 대한 정보는 모델이 스스로 추론해야 한다. 이 논문은 이 숨겨진 runtime semantics를 명시적 지도 대상으로 바꾸는 것이 핵심이다.

### 3. trajectory supervision과 정책 증류

trajectory supervision은 에이전트가 거쳐 간 상태와 행동의 연속, 즉 trajectory를 학습 데이터로 쓰는 방식을 말한다. 여기서 지도 신호는 어떤 history가 주어졌을 때 어떤 action이 취해졌는지에 대한 기록이다. 그런데 이 방식은 행동이 실행된 배경의 runtime control state를 명시하지 않는다는 한계가 있다. 정책 증류(policy distillation)는 더 나아가 교사 정책의 조건부 분포 전체를 학생 정책에 맞추는 방법으로, 특정 context 분포에서 교사가 내놓는 행동 분포와 학생이 내놓는 행동 분포 사이의 KL divergence를 줄이는 손실을 사용한다. 이 논문에서 HPD는 이 정책 증류의 틀에 runtime semantics를 추가하여, action뿐 아니라 control document까지 함께 지도하는 변형이다.

### 4. privileged information

privileged information은 학습 단계에서만 사용할 수 있고 배포 단계에서는 제공되지 않는 정보이다. 예를 들어 어떤 답안이 참고 풀이의 어느 단계까지 맞았는지에 대한 세부 라벨이 학습 때만 주어질 수 있다. 이 논문에서는 replay를 통해 얻은 control document가 privileged information에 해당한다. 교사 모델은 이 document를 추가 입력으로 받아 행동을 생성하므로 더 정확한 판단을 할 수 있지만, 실제 배포 모델은 이 document 없이 원래 harness가 주는 context만 보고 행동해야 한다. privileged information을 쓰는 학습의 핵심은 이 정보가 학생에게 직접 전달되지 않더라도, 공유된 파라미터를 통해 필요한 능력이 내재화되도록 설계하는 것이다. HPD는 문서를 직접 주는 view와 문서를 예측하게 하는 view를 함께 두어 이 내재화를 유도한다.

### 5. replay와 harness verification

replay는 기록된 reference trajectory의 행동들을 harness에 다시 순서대로 넣어 그때의 실행 상태를 재현하는 절차이다. 원래 trajectory 데이터에는 최종 행동만 있고 그 행동이 만들어낸 내부 상태는 사라져 있지만, replay를 하면 harness가 그 행동을 실제로 실행하면서 상태를 전이시키기 때문에 각 모델 호출 직전의 runtime control state를 복원할 수 있다. 이렇게 복원된 상태에서 교사 후보 행동을 생성하고 나면, harness verification이 그 후보가 실제 실행 계약을 만족하는지 검사한다. verification은 행동이 지금 상태에서 실행 가능한지, reference의 lifecycle 단계와 일치하는지, 도구 이름과 정규화된 인자까지 정확히 맞는지를 확인한다. 이 과정을 통과한 행동만 학습 target이 되기 때문에, 단순히 그럴듯한 행동이 아니라 runtime contract를 실제로 통과하는 행동이 지도 신호로 쓰인다.

## 문제의식

기존의 사후 학습 목표들은 대부분 행동 자체를 지도한다. demonstration 기반 학습은 관측된 history를 조건으로 reference action의 likelihood를 높이고, DPO는 선호되는 출력의 상대적 확률을 높이며, RLVR는 실행 가능한 검사로 얻은 보상의 기대값을 최적화한다. 하지만 이들은 모두 그 행동이 의존하는 runtime control state를 따로 명시하지 않는다. 예를 들어 "이 도구를 호출하라"는 action label은 보여주지만, 그 호출이 이미 완료된 일을 반복하는 것인지, 아니면 지금 반드시 수행해야 하는 의무인지는 보여주지 않는다. 실제 제품 환경에서는 이 차이가 치명적이다. 모델이 완료된 작업을 반복 호출하면 불필요한 비용이 들거나 harness가 오류를 내고, 반대로 아직 남은 필수 단계가 있는데 final response를 내면 작업이 실패한다.

이 논문은 정책 불일치를 두 종류로 나눈다. 첫째는 supervision mismatch로, 학습 때 사용한 history 분포와 학생이 실제 rollout에서 만나는 history 분포가 다른 문제이다. 모델이 학습 때 본 reference 경로에서는 잘 따라가지만, 자기 행동이 조금만 어긋나서 낯선 상태로 들어가면 그 다음 행동을 제대로 고르지 못한다. 둘째는 runtime-state mismatch로, 같은 유효한 history에서도 그 순간의 실행 요구 사항이 action label에 암묵적으로 숨어 있는 문제이다. 모델은 어떤 의무가 남아 있는지, 지금 종료가 허용되는지를 history로부터 추론해야 하는데 이것이 잘 안 되면 완료된 일을 반복하거나 끝내면 안 될 때 끝낸다. 이 두 문제는 closed loop 안에서 서로 증폭된다. 한 번 잘못된 행동이 다음 runtime state를 바꾸고, 그 바뀐 state가 또 다음 행동의 context가 되기 때문이다.

기존의 on-policy distillation은 supervision을 학생이 생성한 prefix로 옮겨 supervision mismatch를 줄이지만, 여전히 교사의 행동 분포만 직접 목표로 두어 runtime-state mismatch는 해결하지 못한다. HPD는 이 지점을 겨냥한다. action label이 남긴 암묵적 실행 조건을 명시적인 control document로 복원하고, 이를 학습 목표에 포함시켜 각 decision boundary에서 runtime-compatible한 행동을 배우게 한다.

## 핵심 아이디어

HPD의 핵심 아이디어는 runtime harness가 가진 실행 의미론을 action과 함께 직접 지도하는 것이다. 이를 위해 기록된 reference trajectory를 harness 안에서 replay하여 각 모델 호출 직전의 runtime state를 복원하고, 그 state에서 관측 가능한 사실과 reference에서 온 진행 라벨을 control document라는 텍스트로 만든다. 이 document는 그 시점에 무엇이 완료되었고 무엇이 남아 있으며, 지금 어떤 call이 준비되었고 final permission이 있는지를 명시한다. 그러면 기존 trajectory에서는 history에서 action으로 가는 매핑만 배웠던 것과 달리, 이제는 history에서 control state로 가는 경로와 control state에서 action으로 가는 경로를 분리해서 지도할 수 있다.

왜 이것이 문제를 해결하는가? 먼저, 교사 모델은 이 control document를 privileged information으로 받아 행동을 생성한다. 이는 교사가 runtime state를 추론할 필요 없이 명시적인 조건을 보고 행동을 고르게 해 준다. 그 다음 harness verification이 교사 후보 중 실제로 그 상태에서 실행 가능하고 reference의 제어 결정과 일치하는 것만 남긴다. 따라서 학습 target 자체가 runtime contract를 만족하는 행동이 된다. 마지막으로, 세 가지 view를 한 모델에 함께 학습시켜 이 지식을 배포 정책으로 내재화한다. Runtime view는 native history에서 control document를 예측하게 하고, Injected view는 document를 받아 action을 예측하게 하고, Harness-Replay view는 native context에서 바로 같은 action을 예측하게 한다. 하나의 파라미터를 공유하므로 history에서 control state를 읽는 능력과 control state를 실행 가능한 행동으로 바꾸는 능력이 native action 예측 경로에 스며든다. 배포 시에는 원래 harness interface만 쓰고 document나 추가 모델 호출이 필요 없다.

## 방법

### 1. runtime harness 아래의 closed-loop 실행

task instance $q$가 주어지면 harness $H$의 초기화가 초기 state $s_0$을 만든다. state space $\mathcal{S}_H$에는 실행 history, 도구 인터페이스, permissions, scheduling state, obligation bookkeeping, 남은 예산 같은 전체 runtime 구성이 들어 있다. 모델 호출 직전의 완전한 상태가 $s_b$이고, serializer $\Omega_H$가 이 상태를 모델이 볼 수 있는 텍스트 context $x_b=\Omega_H(s_b)$로 바꾼다. 모델이 action $a$를 출력하면 harness의 transition kernel $T_H(\cdot \mid s,a)$가 다음 state의 분포를 결정한다. 이 kernel은 harness의 parsing, permission check, tool execution, observation insertion, scheduling, stopping code를 모두 포함한다. 특정 state $s$에서 즉시 실행 가능한 action 집합은 $\mathcal{A}_H(s)=\{a:T_H(\bot\mid s,a)=0\}$로 정의된다. 여기서 $\bot$은 치명적 계약 위반이나 예산 소진으로 빠지는 흡수 실패 상태를 뜻한다. 전체 trajectory의 확률은 모델의 행동 확률과 harness의 전이 확률의 곱으로 주어진다. 즉 배포된 에이전트는 모델 $\pi_\theta$ 하나가 아니라 모델, serializer, transition kernel이 함께 만드는 과정이다.

### 2. runtime semantic alignment gap

일반적인 policy distillation 손실은 $\mathcal{L}_{\mathrm{PD}}(\theta;\mu,\pi^T)=\mathbb{E}_{x\sim\mu}[D_{\mathrm{KL}}(\pi^T(\cdot\mid x)\|\pi_\theta(\cdot\mid x))]$이다. 여기서 $\mu$는 context 분포, $\pi^T$는 교사 조건부 분포, $D_{\mathrm{KL}}$은 forward KL divergence이다. 이 손실에서 context 분포가 reference boundary들과 다르면 supervision mismatch가 생긴다. 또 주어진 boundary에서 조건부 target이 runtime control state를 반영하지 않으면 runtime-state mismatch가 생긴다. HPD는 reference-history boundary에서 control label과 함께 검증된 action을 지도하고, 그렇게 필터링된 context 분포 $\mu_H^{\mathrm{rep}}$ 위에서 학습한다.

### 3. HPD의 세 단계

첫 단계는 verified replay와 control-document construction이다. 기록된 trajectory $\tau^\star$의 각 reference action $a_b^\star$를 harness에 다시 넣어 replay하면서, 다음 boundary의 state $s_{b+1}^\star$를 얻는다. 관측 어댑터 $\operatorname{Observe}_H$가 state에서 runtime field snapshot $o_b^H$를 읽고, 결정적 컴파일러 $\Phi_H$가 이 snapshot과 reference annotation을 텍스트 control document $d_b^H$로 변환한다. document에는 관측된 runtime 사실, reference 단계 진행 상황, 그리고 witness에서 얻은 ready frontier와 final permission 라벨이 들어 있다. 이 관측-컴파일 과정을 AutoProbe라고 부른다.

둘째 단계는 harness-verified privileged teacher이다. frozen base model $\theta_0$에 $\operatorname{Inject}_H(x,d)$라는 프롬프트로 control document를 주입하고 $K=2$개의 후보 행동을 샘플링한다. 각 후보 $\tilde{a}_b^{(k)}$에 대해 verifier $V_{H,b}$가 admissibility, reference-stage consistency, tool 이름과 정규화된 인자의 정확한 일치 여부를 검사한다. 통과한 후보 중에서 reference와의 cosine similarity가 가장 높은 것을 선택해 학습 target $\tilde{a}_b$로 삼는다. replay는 원래 reference action $a_b^\star$로 진행하므로 학습에 쓰는 history는 reference prefix를 유지한다. 각 retained record는 $(x_b^\star, d_b^H, \tilde{a}_b)$이다.

셋째 단계는 three-view training이다. 한 공유 모델에 세 가지 프롬프트 계약을 둔다. $\pi_\theta^T(a\mid x)$는 native context에서 행동을 예측하는 Harness-Replay view, $\pi_\theta^I(a\mid x,d)$는 document를 받아 행동을 예측하는 Injected view, $\pi_\theta^R(d\mid x)$는 native context에서 document를 재구성하는 Runtime view이다. 손실은 $\mathcal{L}_{\mathrm{HPD}}=\alpha_T\mathcal{L}_T+\alpha_I\mathcal{L}_I+\alpha_R\mathcal{L}_R$이고 가중치 합은 1이다. sequence-level distillation에서는 완성된 시퀀스 $y$가 point mass target이므로 KL divergence는 음의 로그 우도 $-\log\pi_\theta(y\mid c)$가 된다. 구현에서는 이를 completion length로 나눈 $\ell_\theta(y,c)=-\frac{1}{|y|}\sum_{j=1}^{|y|}\log\pi_\theta(y_j\mid c,y_{<j})$를 사용한다. T와 I는 같은 검증된 행동 $\tilde{a}_b$를 맞추고, R은 document $d_b^H$를 맞춘다. 배포 시에는 $\pi_\theta^T$만 사용한다.

## 왜 성립하는가

이 방법이 성립하는 이유는 크게 두 가지로 나눌 수 있다. 하나는 교사 분포의 분해 구조이고, 다른 하나는 shared parameter를 통한 내재화이다.

교사 분포 측면에서, retained record 하나는 context $x$, document $d$, action $a$의 쌍으로 이루어진다. 이를 결합 분포 $\pi^{\mathrm{rep}}(d,a\mid x)=\pi_R^{\mathrm{rep}}(d\mid x)\pi_I^{\mathrm{rep}}(a\mid x,d)$로 쓸 수 있다. KL chain rule에 따르면 결합 분포를 맞추는 문제는 document marginal을 맞추는 문제와 document가 주어졌을 때 action 조건부를 맞추는 문제로 정확히 분해된다. 이 분해가 바로 Runtime view와 Injected view 손실의 정당성이다. 또 teacher의 native action marginal $\pi_T^{\mathrm{rep}}(a\mid x)$는 같은 결합 분포에서 document를 모두 합한 값이므로, Harness-Replay view는 배포 시 필요한 native 조건부를 직접 맞춘다. 따라서 세 손실은 각각 결합 교사 분포의 다른 측면을 지도하며, 합쳐졌을 때 history에서 control state로, control state에서 action으로, history에서 action으로 가는 세 경로를 모두 덮는다.

point mass target에서는 또 하나의 단순화가 생긴다. 교사가 특정 action 하나에 확률 1을 주는 hard target이면 학생의 그 action 로그 확률을 높이는 것이 곧 KL divergence를 줄이는 것과 같아진다. 교사 엔트로피 항은 상수가 되어 빠진다. 따라서 매 record에 대해 negative log likelihood를 평균하는 구현이 조건부 교사 분포에 대한 forward KL 최적화와 일치한다. 여기에 verification이 더해져 그 hard target 자체가 runtime contract를 만족하는 행동으로 제한된다. 즉 학습 target의 품질과 손실의 수학적 성질 양쪽에서 정당화가 된다.

shared parameter 측면에서는, Runtime view가 native history에서 document를 예측하도록 강제하므로 모델의 native context 표현 안에 남은 obligation, ready call, termination 조건 등이 인코딩된다. Injected view는 그 document가 주어졌을 때 어떤 action을 선택해야 하는지를 배운다. Harness-Replay view는 같은 backbone에서 document 없이 곧바로 action을 예측하는 경로를 학습한다. 세 view가 파라미터를 공유하므로 R과 I에서 생긴 control-state 지식이 T의 native action 예측 경로에도 반영된다. 실제로 실험에서 HPD-T만 쓸 때보다 T/I/R을 함께 쓸 때 task success가 20.58에서 22.98로, Step-SR이 59.25에서 63.79로, RC가 43.74에서 49.23으로 오른다. 이는 control document 지도가 native action 지도에 더해져 완료와 실행 준수를 개선했다는 실험적 근거가 된다. 반대로 T 다음에 R만 이어서 학습하는 staged 방식은 TS가 20.58에서 7.03으로 급락하는데, 이는 interleaving으로 native action 지도를 계속 유지하는 것이 중요하다는 점을 보여준다.

## 구체적 예시

논문에서 든 lookup 예시를 따라가 보자. 어떤 계약이 "lookup(item_id=42)를 호출한 뒤에만 final response를 할 수 있다"고 정하고, replay queue에 value=7이라는 관측이 들어 있다고 하자. 처음 모델 호출 직전 상태에서는 lookup 의무가 아직 남아 있고 finalization은 차단되어 있다. 이 상태를 AutoProbe가 문서로 만들면 lookup=pending; final=blocked가 된다. 그 다음 기록된 lookup 호출을 replay하면 harness가 그 도구를 실행하고 queue에서 value=7을 꺼내 관측으로 삽입한다. 이제 lookup 의무가 완료되고 finalization이 허용된다. 다음 boundary의 문서는 lookup=complete; final=ready가 된다. 이처럼 동일한 도구가 "사용 가능하다"는 사실만으로는 알 수 없는 실행 조건이 document를 통해 명시적으로 드러난다.

이 예시는 왜 action label만으로는 부족한지를 보여준다. 첫 boundary에서 모델이 lookup 호출을 reference action으로 학습한다고 해도, 그 행동이 "지금 반드시 해야 하는 미완 의무" 때문인지 아닌지는 label에 없다. 그래서 학습 후 모델이 다른 rollout에서 lookup을 이미 완료한 뒤에도 다시 호출하거나, 반대로 아직 완료하지 않았는데 final response를 내는 실수를 할 수 있다. HPD는 첫 상태에서는 lookup=pending; final=blocked를, 두 번째 상태에서는 lookup=complete; final=ready를 각각 지도함으로써 이 구분을 모델이 예측할 수 있게 만든다.

실제 수치 예시로는 Table 1의 SFT가 좋은 반면교사다. SFT는 reference action을 그대로 학습했을 때 Step-SR이 26.45에서 47.20으로, RC가 19.90에서 55.92로 크게 오른다. 그런데 TS는 3.09에서 오히려 2.06으로 떨어지고 F1도 26.82에서 2.40으로 급락한다. reference 경로의 action을 맞추는 능력은 올랐지만, 자기 rollout에서는 답변 품질과 작업 완료가 무너진 것이다. 같은 표에서 HPD는 RC가 49.23으로 SFT보다 낮지만 TS는 22.98로 훨씬 높다. execution compliance만 높다고 해서 태스크를 끝까지 완료하는 것은 아니라는 뜻이다. 또 OPD는 RC 66.21로 가장 높지만 TS는 15.61에 그친다. HPD는 OPD보다 RC는 낮아도 TS와 Exact에서 앞선다. 이는 compliance가 높은 것과 실제로 끝까지 성공하는 것이 순위가 다를 수 있음을 보여주는 구체적 수치다.

## 실험과 결과

실험은 Qwen3-8B에 LoRA를 적용하고 TRAJECT-Bench의 583개 held-out 태스크를 Pi harness에서 평가한다. 지표는 task success, final-answer F1, gold-history action accuracy, reference-prefix step success, runtime compliance, exact-path success의 여섯 가지다. base model은 TS 3.09, F1 26.82, RC 19.90을 기록한다. 반면 HPD는 TS 22.98, F1 41.22, Step-SR 63.79, RC 49.23, Exact 18.70을 기록한다. TS는 base에 비해 약 7.4배 수준이고, RC는 2.5배 가까이 오른다. HPD의 TS 22.98은 가장 강한 기존 baseline인 OPD의 15.61보다 7.38포인트 높고, 상대적으로는 47.3% 높다. 반면 F1은 HPD 41.22, OPD 41.04로 거의 같다. 즉 HPD는 답변 겹침 측면에서는 OPD와 비슷하면서도 실제 완료된 태스크 수에서는 훨씬 앞선다.

Table 1에서 두드러지는 비교는 HPD-T와 HPD의 차이다. HPD-T는 같은 document-conditioned, verifier-selected teacher target을 쓰지만 native replay-action view만 학습한다. HPD-T는 TS 20.58, Step-SR 59.25, RC 43.74를 기록한다. Full HPD는 여기에 I/R view를 더해 TS 22.98, Step-SR 63.79, RC 49.23으로 올린다. 특히 TS는 HPD-T 대비 2.40포인트, Exact는 3.09포인트 오른다. 이는 검증된 teacher action 자체의 기여와 control document 지도의 기여를 분리해서 보여준다. 반면 DPO는 Action-Acc 72.38로 가장 높지만 Step-SR 11.12, TS 7.20에 그친다. DPO의 장점은 지역적으로 reference action을 선호하게 만드는 것이지 전체 실행 경로나 완료로 이어지지 않는다는 해석이 가능하다.

Table 2의 component ablation은 20k batch exposure를 각 view에 맞춰 비교한다. T+R joint는 TS가 HPD-T와 같은 20.58이지만 Step-SR은 59.25에서 63.13으로, RC는 43.74에서 48.03으로 오른다. T+I joint는 TS를 올리지 못하고 오히려 실행 지표가 내려간다. 오직 T/I/R을 모두 함께 interleaving한 경우에만 TS가 22.98로 올라간다. staged 방식은 더 극적이다. T 다음에 R을 순차 학습한 T→R은 TS가 20.58에서 7.03으로, RC가 43.74에서 18.35로 폭락한다. T→I 역시 TS 18.01, RC 34.99로 내려간다. 이는 같은 view라도 전체 학습 동안 native action 지도를 유지하는 interleaving이 중요하다는 것을 보여준다.

cross-benchmark transfer에서도 효과가 이어진다. BFCL v4의 92개 태스크에 대해 재학습 없이 TRAJECT-Bench checkpoint를 평가하면 HPD는 TS 21.74, Step-SR 48.12를 기록한다. base는 TS 13.04, Step-SR 42.03이다. HPD-T는 TS 13.04로 base와 같지만 F1 26.12로 가장 높다. 즉 HPD-T는 답변 겹침과 prefix 실행을 일부 옮기지만 새 태스크에서 완료율은 올리지 못하고, Full HPD에서 I/R view가 추가되어 TS가 8.70포인트 오른다. 이는 control document 지도가 특정 태스크 분포에 과적합되기보다 harness 정책 자체의 정렬을 강화한다는 주장을 뒷받침한다.

모델 크기와 architecture를 바꾼 실험에서도 일관되게 이득이 있다. Qwen3 크기를 0.6B부터 32B까지 바꾸면 모든 크기에서 HPD가 Base보다 TS와 F1이 높다. 0.6B는 TS 0.00에서 4.46으로, 32B는 TS 6.00에서 19.90으로 오른다. Llama3-8B는 TS 0에서 20.07 포인트를 얻고, Gemma4-12B는 16.47 포인트, Qwen3-30B-A3B는 12.69 포인트를 얻는다. Pi 외에 ReAct, Compiler, OpenCode harness에도 따로 적응시키면 TS가 9.44에서 18.35 포인트 오른다. 이는 HPD의 재생-검증-세 view 구조가 특정 모델이나 특정 harness에 국한되지 않는다는 증거다.

API 모델과의 비교에서는 같은 Pi agent와 평가 설정에서 HPD의 TS 22.98이 DeepSeek V4 Flash의 22.30보다 높고, F1은 GPT-5.4-mini가 41.92로 HPD의 41.22보다 약간 높다. HPD는 오픈 Qwen3-8B를 특정 harness에 적응시킨 checkpoint로, 훨씬 큰 API 모델들과 완료율 기준에서 비슷하거나 나은 수준에 도달한다는 의미가 있다.

## 한계

논문이 명시적으로 인정한 한계는 harness-specific adaptation이다. HPD는 지정된 runtime 계약에 대해 정책을 학습시키므로 다른 harness에 적용하려면 교사 구축 과정을 다시 만들고 별도의 adapter를 훈련해야 한다. 실험은 이 per-harness adaptation 절차를 평가하지만, 하나의 adapter가 여러 harness에서 동시에 작동하는 범용성을 보여주지는 않는다.

두 번째 한계는 reference replay가 성공한 reference prefix를 주로 다룬다는 점이다. 학습 분포가 배포 후 발생할 수 있는 오류 상태까지 충분히 덮지 못할 수 있다. 논문은 online extension이 필요하며, deployment error 이후 상태까지 훈련하려면 그 상태들에 대해 검증된 correction이 필요하다고 인정한다. 이는 supervision mismatch를 완전히 해소했다기보다는 성공 경로 주변의 mismatch를 줄인 것으로 해석된다.

세 번째로 verifier coverage의 제약이 있다. teacher construction은 지정된 harness-policy와 tool-call 부분에서 reference와 정확히 일치할 것을 요구한다. TRAJECT-Bench evaluation에서 argument-level 기준은 required parameter key의 일치이고, tool 출력은 고정 replay queue를 사용한다. 따라서 이 기준이 실제 제품에서 발생하는 더 복잡한 인자 의미나 도구 출력의 변화를 모두 포착하지는 못한다. control document의 일부 라벨은 reference 단계와 current action witness를 쓰는 privileged supervision이라, 그 라벨이 없는 실제 rollout 상태에서는 동일한 품질이 보장되지 않을 수 있다.

또한 읽으면서 드러나는 약점으로, HPD의 RC 49.23은 OPD의 66.21보다 낮다. HPD가 완료율에서는 더 높지만 실행 계약 준수율 자체를 최대화한다고는 말하기 어렵다. metric 간 trade-off가 있을 수 있고, 어떤 제품 환경에서 준수율이 더 중요한지에 따라 OPD 계열이 더 적합할 수도 있다. 논문은 TS와 RC가 다른 것을 측정한다고 분리하지만, HPD가 모든 실행 지표에서 최고인 것은 아니다. signal-density search에서도 어떤 view 빈도를 높이는 것이 TS에 좋은지 RC에 좋은지가 갈린다. 이는 최적 가중치가 지표에 따라 달라진다는 뜻으로, 실무에서 목표 설정이 필요함을 보여준다.

## 왜 중요한가

실무적으로 이 논문은 조직이 자체 제품 harness에 일반 모델을 적응시킬 때 무엇을 지도해야 하는지에 대한 관점을 바꾼다. 단순히 더 많은 trajectory나 더 나은 action 분포를 모방하는 대신, harness가 강제하는 실행 의미론을 명시적인 control document로 만들어 학습 목표에 포함시킬 수 있다. 이렇게 하면 학습 데이터 안에 없던 새로운 태스크에서도 runtime 계약을 따르는 일반화가 개선된다는 점이 BFCL transfer 실험에서 드러난다. 특히 HPD는 배포 시 추가 문서나 추가 모델 호출이 필요 없고 원래 harness interface를 그대로 쓰기 때문에, 실제 시스템에 붙이기 쉬운 구조다.

학술적으로는 privileged information을 쓰는 distillation과 process supervision, runtime evaluation의 경계를 연결한다. 기존의 privileged information 연구는 학습 때만 주어지는 정보로 학생을 지도했지만, HPD는 이를 harness의 lifecycle이라는 구조화된 실행 상태에 적용하고 세 view의 공유 파라미터로 내재화한다. KL chain rule을 통해 R과 I가 결합 분포의 분해를 이루고 T가 native marginal을 맞춘다는 점은, 정책 증류의 목표를 action 분포에서 runtime semantics를 포함한 결합 분포로 확장하는 이론적 틀을 제공한다.

후속 연구로는 deployment error 이후 상태를 포함하는 online correction, 더 일반적인 verifier와 argument-level criterion, 여러 harness를 동시에 다루는 정책 등이 가능하다. 또 HPD의 TS와 RC 사이 trade-off를 세밀히 분석하여 어떤 제품에서는 compliance를 우선하고 어떤 제품에서는 completion을 우선해야 하는지에 대한 지침이 필요하다. 논문은 "무엇을 할지"뿐 아니라 "어떤 실행 조건을 고려해야 할지"를 지도하는 방향이 agent 정책 정렬에서 실질적 완료율과 실행 계약 준수 모두에 기여할 수 있음을 보여준다.

## 원문 초록

> Deploying a general-purpose model as an agent means running it inside a product-specific runtime harness that decides which actions are executable, how state advances, and when the loop may terminate. Ordinary trajectory supervision shows which action was taken but leaves the runtime semantics behind that action implicit. We introduce Harness Policy Distillation (HPD), which makes these runtime control semantics an explicit training target alongside actions to align the harness policy. HPD replays reference trajectories through the harness to recover the runtime semantics that are implicit in ordinary trajectory data, and represents them as control documents at each model-call boundary. These documents provide privileged information for a teacher to generate actions, while harness verification ensures that the resulting targets are executable under the runtime contract. We jointly train a shared model on the runtime semantics recovered from control-state privileged information and native history, thereby internalizing these semantics into the model policy. At deployment, the trained model uses the original harness interface without requiring the control document or any additional supplement. On TRAJECT-Bench with the Pi harness, Qwen3-8B trained with HPD reaches 22.98% autonomous task success and 49.23% runtime compliance, against 3.09% and 19.90% for the unadapted model. Harness-verified teacher actions substantially improve the native deployment policy, while joint control-state supervision provides further gains in task completion and runtime compliance. HPD turns executable runtime semantics into dense supervision for learning harness-compatible actions at each decision boundary.
