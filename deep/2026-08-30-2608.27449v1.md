## 한 줄 요약

SWE-Prime은 성공한 coding agent trajectory 전체를 SFT에 쓰지 않고, trajectory 수준과 semantic segment 수준에서 품질·다양성·학습 가치를 평가해 10%의 trajectory만으로 전체 성공 trajectory보다 높은 SWE-Bench 성능을 얻는 데이터 선택 방법이다.

## 핵심 개념 풀이

### Coding agent trajectory

이 논문에서 trajectory란 언어 모델이 소프트웨어 issue를 해결하기 위해 저장소를 탐색하고, 파일을 수정하고, 테스트를 실행하고, 그 결과를 확인하는 일련의 행동과 관찰 기록을 뜻한다. 최종 patch만 저장하는 것이 아니라, 에이전트가 어떤 경로로 답에 도달했는지를 타임라인처럼 남긴 것이다. 예를 들어 "README를 읽는다 → 함수 정의를 검색한다 → 파일을 수정한다 → 테스트를 돌린다 → 통과했다" 같은 흐름 전체가 하나의 trajectory다. SFT에서는 이 기록 전체를 학습 sequence로 쓰기 때문에, 최종 결과뿐 아니라 중간 과정도 모델이 따라 하게 된다.

### Supervised Fine-Tuning과 loss mask

Supervised Fine-Tuning, 즉 SFT는 언어 모델이 demonstration의 다음 token을 잘 예측하도록 파라미터를 갱신하는 학습 방식이다. coding agent SFT에서는 여러 turn에 걸쳐 assistant가 만들어 낸 action token들의 확률을 높이는데, 여기서 무엇을 loss에 포함하느냐가 중요하다. 일반 SFT는 trajectory 전체에서 assistant가 생성한 모든 token에 gradient를 주지만, loss mask를 쓰면 특정 구간만 gradient를 주고 나머지는 context로만 남길 수 있다. 이 논문에서 loss mask는 "모델이 볼 수 있는 정보"와 "모델이 따라 하도록 압박받는 demonstration"을 분리하는 장치다.

### Semantic segment

semantic segment는 개별 step보다 크고 trajectory 전체보다 작은 단위로, 공통 의도를 가진 연속된 step들을 묶은 구간이다. 소프트웨어 문제 해결에서 하나의 행동은 보통 여러 action과 observation에 걸쳐 나타난다. 예를 들어 "특정 심볼이 저장소 어디에서 쓰이는지 추적한다"는 탐색 행동은 파일 열기, 검색, 결과 읽기 등 여러 step으로 구성된다. 이런 구간을 개별 step으로 쪼개면 의도와 기여도를 판단하기 어렵고, trajectory 전체로 보면 local한 쓰레기 구간이 묻힌다. 그래서 SWE-Prime은 behavior 단위 평가를 위해 semantic segment를 쓴다.

### Process quality와 result quality

task success는 final patch가 테스트를 통과했는지만 보는 outcome 지표다. 반면 process quality는 그 결과를 얻기까지의 과정이 좋은 demonstration인지를 본다. 이 논문에서는 저장소를 먼저 탐색하고 나중에 검증하는 observe-edit-verify 흐름, tool call 성공률, 인접 중복 행동, git history로 정답 정보를 미리 보는 leakage 같은 신호로 process quality를 잰다. result quality는 최종 patch가 필요한 범위만 수정했는지를 본다. 테스트를 통과해도 불필요한 파일까지 고치면 학습 데이터로는 나쁜데, 모델이 over-edit을 배울 수 있기 때문이다.

### Data representativeness와 HDBSCAN

품질 점수만으로 상위 trajectory를 고르면 비슷한 유형의 issue에 편중될 수 있다. 예를 들어 특정 패턴의 Python 버그가 품질 점수가 높다고 그것만 뽑으면, 다른 언어나 다른 수정 패턴에 대한 coverage가 사라진다. 이를 막기 위해 issue 설명을 embedding한 뒤 HDBSCAN으로 군집화한다. HDBSCAN은 density 기반 clustering 방법으로, 사전에 군집 수를 정하지 않아도 되고 outlier를 따로 처리할 수 있다. 군집별로 trajectory를 나눠 뽑으면 다양성과 대표성을 함께 유지할 수 있다.

## 문제의식

기존 연구들은 대규모 software engineering trajectory dataset을 만들고, 실행 검증을 통과한 성공 trajectory에 SFT를 적용해 coding agent의 issue 해결 능력을 높이려 했다. SWE-Gym, SWE-smith, R2E-Gym 같은 데이터셋 구축 방식이 대표적이다. 그런데 "테스트를 통과했다"는 것은 최종 patch가 정답 조건을 만족했다는 뜻일 뿐, 그 trajectory의 모든 step이 학습할 가치가 있다는 뜻은 아니다.

성공한 trajectory에도 비효율적이거나 중복되거나 위험한 step이 섞여 있을 수 있다. 예를 들어 어떤 trajectory는 코드 수정 전에 저장소를 제대로 탐색하지 않고 바로 파일을 바꿀 수 있다. 또 다른 trajectory는 tool call이 자주 실패하거나, 이미 확인한 정보를 다시 얻기 위해 같은 명령을 반복할 수 있다. 더 심각한 경우로는 git history에서 미래의 정답 patch 정보를 읽어 와서 그 정보로 코드를 고치는 leakage shortcut이 있다.

이런 행동이 포함된 trajectory 전체를 SFT에 쓰면, 모델은 final patch가 성공했더라도 나쁜 문제 해결 패턴을 따라 하게 된다. 예를 들어 학습 후 모델이 실제로는 알 수 없는 미래 정보에 의존하려 하거나, 문제와 무관한 파일까지 과도하게 수정하거나, 같은 탐색을 반복해 interaction turn을 낭비할 수 있다. 기존의 일부 필터링은 tool call이 실패한 step만 loss에서 제외하는 정도였지만, 명시적인 에러가 없는 중복·무관·위험 행동은 걸러내지 못했다.

또한 trajectory 전체가 좋아 보여도 그 안의 특정 구간은 최종 해결에 기여하지 않는 경우가 있다. 해당 구간의 step들이 실행만 성공할 뿐 실제 수정에는 아무 도움이 안 되거나, 오히려 위험한 습관을 가르칠 수 있다. 따라서 높은 품질의 SFT supervision은 "성공했다"는 결과만으로 판단할 수 없고, trajectory 단위와 그보다 미세한 segment 단위를 함께 봐야 한다.

## 핵심 아이디어

SWE-Prime의 본질은 supervision의 단위를 점점 좁히는 two-stage selection이다. Stage 1에서는 전체 trajectory pool에서 품질이 낮거나 대표성이 떨어지는 trajectory를 걸러낸다. Stage 2에서는 남은 trajectory 내부에서도 semantic segment 단위로 학습 가치가 높은 구간만 loss에 포함한다. 이렇게 하면 "전체 데이터를 다 쓰는 것보다 적은 데이터로 더 나은 성능"을 얻을 수 있다.

Stage 1이 process quality, result quality, data representativeness를 함께 보는 이유는 각각 서로 다른 실패 모드를 잡기 때문이다. process quality는 에이전트가 문제를 푸는 과정 자체가 모범적인지를, result quality는 patch가 필요한 범위만 수정했는지를, representativeness는 선택된 subset이 다양한 issue 유형을 덮는지를 확인한다. 이 세 조건이 함께 있어야 compact하면서도 general한 학습 데이터가 된다.

Stage 2의 핵심은 "전체 trajectory는 context로 남기되, 선택된 segment만 loss에 기여시킨다"는 것이다. 이렇게 하면 unselected segment에 담긴 낮은 품질의 행동은 gradient를 만들지 않는다. 하지만 그 segment의 token은 여전히 sequence 안에 있기 때문에 이후 selected segment가 그 앞의 맥락을 잃지 않는다. context 보존과 supervision 정제라는 두 목표를 동시에 달성하는 설계다.

이 아이디어가 문제를 푸는 논리는 다음과 같다. SFT는 결국 어떤 token 분포를 높일지를 결정하는 문제인데, 성공 trajectory 전체에 loss를 주면 성공과 무관한 행동까지 강화된다. 반대로 trajectory 단위로만 필터링하면 좋은 trajectory 안에 숨은 local한 저품질 구간이 남는다. SWE-Prime은 trajectory 수준에서 큰 noise를 제거하고, segment 수준에서 남은 작은 noise를 제거하는 계층적 구조이므로 supervision이 훨씬 깨끗해진다.

## 방법

Stage 1은 먼저 각 성공 trajectory에 대해 네 가지 process quality 신호를 계산한다.
첫째, $S_{\mathrm{workflow}}$는 trajectory가 첫 수정 전에 저장소를 탐사했고, 마지막 수정 후 테스트나 검사로 patch를 검증했으면 1, 아니면 0이다. 이는 observe-edit-verify라는 체계적인 문제 해결 패턴을 측정한다.
둘째, $S_{\mathrm{tool}}$은 trajectory의 tool call 성공률을 전체 trajectory pool 안에서의 percentile rank로 변환한 값이다. 같은 성공률이라도 전체 pool의 분포에 따라 상대적으로 얼마나 안정적인 tool 사용인지 알 수 있다.
셋째, $S_{\mathrm{redundancy}}$는 인접한 두 tool call이 같은 이름과 같은 인자를 반복하면 0, 그런 인접 중복이 없으면 1이다. 이는 에이전트가 이전 행동을 잊고 같은 명령을 반복해 새로운 정보 없이 context만 늘리는 continuous redundancy를 잡는다.
넷째, $S_{\mathrm{git}}$은 git history 조작이 코드 수정 전에 미래 reference patch 정보를 노출했는지를 보고 leakage가 있으면 0, 없으면 1이다. 이는 에이전트가 실제로는 쓸 수 없는 미래 정보를 shortcut으로 쓰는 행동을 차단한다.

Stage 1의 result quality는 생성 patch의 수정 범위를 reference patch와 비교한다.
$F_{\mathrm{model}}$과 $F_{\mathrm{gold}}$는 각각 생성 patch와 reference patch가 수정한 파일 수를 뜻하고, $L_{\mathrm{model}}$과 $L_{\mathrm{gold}}$는 변경된 줄 수를 뜻한다.
파일 범위 점수는
$$S_{\mathrm{file}}=\min\left(\frac{F_{\mathrm{gold}}}{F_{\mathrm{model}}},1\right)$$
로 정의한다. 생성 patch가 reference보다 파일을 더 많이 수정하면 분수 값이 1보다 작아져 점수가 낮아진다.
줄 범위 점수도
$$S_{\mathrm{line}}=\min\left(\frac{L_{\mathrm{gold}}}{L_{\mathrm{model}}},1\right)$$
로 같은 방식으로 계산한다.
최종 result quality 점수는
$$S_{\mathrm{result}}=S_{\mathrm{file}}\times S_{\mathrm{line}}$$
이다. 곱셈을 쓰는 이유는 파일 범위와 줄 범위가 모두 집중되어 있을 때만 높은 점수를 주기 위해서다. 예를 들어 파일 수는 reference와 같아도 줄 수가 지나치게 많으면 $S_{\mathrm{line}}$이 낮아져 전체 점수가 낮아진다.

이후 다섯 신호를 평균해 trajectory 품질 점수를 만든다.
$$S_{\mathrm{traj}}=\frac{1}{5}\left(S_{\mathrm{workflow}}+S_{\mathrm{tool}}+S_{\mathrm{redundancy}}+S_{\mathrm{git}}+S_{\mathrm{result}}\right)$$
이 값이 높을수록 process가 안정적이고 result가 집중된 trajectory다.

다음으로 대표성 평가를 위해 issue 설명을 Qwen3-Embedding-8B로 embedding하고 HDBSCAN으로 군집화한다. 군집에 속하지 않은 issue는 따로 처리한다. 각 군집 안에서 $S_{\mathrm{traj}}$로 정렬한 뒤 예산 내에서 높은 순위부터 선택한다. 이렇게 하면 품질만 높은 trajectory가 아니라 issue 유형별로 다양한 trajectory가 선택된다. Stage 1에서 선택된 trajectory들이 Stage 2의 후보 집합이 된다.

Stage 2는 먼저 trajectory를 semantic segment로 나눈다. 이때 개별 step이 아니라 연속된 step들을 공통 의도로 묶는다. long trajectory는 LLM의 context window를 넘어설 수 있으므로 sliding window로 처리하는데, 고정 크기 window는 경계에서 진행 중인 behavior를 잘라 마지막 segment의 끝을 잘못 판단하게 만들 수 있다. 이를 막기 위해 SWE-Prime은 boundary-aware chunking을 쓴다. 각 window를 처리한 뒤 마지막 segment만 확정하지 않고 다음 window로 넘겨 뒤따르는 step들과 함께 다시 평가한다. 또한 window 사이에는 task 목표, 확정된 사실, 발견된 위험을 compact summary로 전달해 segmentation 일관성을 유지한다.

Segment scoring에서는 LLM이 issue 설명, trajectory context, reference patch를 보고 각 segment $s_{i,j}$에 0부터 10까지의 품질 점수 $q_{i,j}$와 근거를 부여한다. 평가 기준은 세 가지다.
첫째, final fix에 대한 기여도다. issue localization, context gathering, modification, verification, error recovery 중 하나라도 진전시켰다면 기여가 있다고 본다.
둘째, local learnability다. 그 시점에서 이용 가능한 정보만으로 명확한 evidence–action–feedback 패턴을 보여주는지 평가한다.
셋째, behavioral risk다. 무관한 탐색, 정보가 없는 실패, 안전하지 않은 작업, hardcoded solution 같은 바람직하지 않은 행동을 잡는다.

Segment filtering에서는 점수에 binary selection mask를 만든다.
$$m_{i,j}=1 \quad\text{if}\quad q_{i,j}\ge \delta$$
그렇지 않으면 $m_{i,j}=0$이다. 여기서 $\delta$는 segment score threshold이며 논문에서는 7로 설정했다.
모든 segment는 sequence에 남아 context로 쓰이지만, loss는 selected segment 안의 assistant-response token에만 적용된다.
$y_i$를 trajectory $i$의 전체 token sequence라고 하고, $\mathcal{A}(s_{i,j})$를 segment $s_{i,j}$ 안에서 assistant가 생성한 token 위치 집합이라고 하면 selective SFT objective는 다음과 같다.
$$\mathcal{L}_{\mathrm{SFT}}=-\frac{1}{N_{\mathrm{sel}}}\sum_{i}\sum_{j}m_{i,j}\sum_{t\in \mathcal{A}(s_{i,j})}\log p_\theta(y_{i,t}\mid y_{i,<t})$$
여기서 $N_{\mathrm{sel}}$은 selected segment에 속한 assistant-response token의 총 개수로, loss를 평균 token 수준으로 정규화한다. $y_{i,<t}$는 t번째 token 이전까지의 모든 context token이다. 즉 모델은 unselected segment의 token도 조건부 입력으로는 보지만, 그 구간의 assistant token을 예측하는 loss는 만들지 않는다.

## 왜 성립하는가

이 논문은 이론적 증명보다 실험적 근거로 주장을 뒷받침한다. 성립 이유는 크게 두 갈래로 이해할 수 있다. 첫째는 Stage 1이 SFT에 해로운 trajectory를 제거한다는 점이고, 둘째는 Stage 2가 남은 trajectory 내부의 학습 신호까지 정제한다는 점이다.

Stage 1의 각 신호는 모델이 배워서는 안 되는 구체적인 행동에 대응한다. 저장소 탐색 없이 바로 수정하는 trajectory를 학습하면 모델도 evidence 없이 편집부터 하는 행동을 배울 수 있다. tool call 실패가 잦은 trajectory는 불안정한 도구 사용 패턴을 가르친다. 같은 명령을 반복하는 trajectory는 long-context를 비효율적으로 쓰는 습관을 강화한다. git history leakage가 있는 trajectory는 실제 추론 시에는 불가능한 shortcut에 의존하게 만든다.

Result quality의 곱셈 구조도 효과적이다. 파일 수만 적고 줄 수가 지나치게 많은 patch, 또는 줄 수만 적고 파일을 과도하게 건드리는 patch는 한쪽 점수가 낮아져 최종 점수가 낮아진다. 따라서 Stage 1은 "통과했지만 지저분한 patch"를 걸러낼 수 있다.

Representativeness는 품질 필터링의 부작용을 막는다. 품질 점수 상위만 고르면 모델이 자주 등장하는 issue 유형에 overfitting할 수 있다. HDBSCAN 군집 안에서 상위 trajectory를 고르면 학습 subset의 coverage가 유지되고, 다양한 언어와 issue 유형에 대한 일반화 가능성이 높아진다. 실험에서도 Python, JavaScript, TypeScript, Go 모든 언어 subset에서 SWE-Prime이 가장 좋은 결과를 냈다는 점이 이를 뒷받침한다.

Stage 2의 효과는 ablation에서 분명하게 나타난다. Stage 1만 적용한 w/o Stage 2보다 SWE-Prime이 모든 평가 setting에서 높은 Resolved Rate를 기록했다. 예를 들어 GLM-4.7-Flash의 SWE-Bench Verified에서 Stage 1만 쓰면 43.6인데, segment-level selection을 더하면 51.4가 된다. 이는 좋은 trajectory 안에도 loss에서 빼야 할 local한 저품질 구간이 있다는 주장을 실험적으로 보여준다. Random-10%가 raw model보다 낮아지는 경우가 있다는 점도 같은 데이터 양이라도 무엇을 고르고 어떤 토큰을 loss에 넣는지가 결정적임을 시사한다.

## 구체적 예시

Table 1의 GLM-4.7-Flash 행을 따라가면 SWE-Prime의 효과가 명확하게 드러난다.
SWE-Bench Verified에서 raw model은 40.4를 기록했다. 이는 500개 검증 task 중 약 202개를 해결했다는 뜻이다.
성공 trajectory 전부인 32,161개로 SFT한 Resolved-Trajectory SFT는 41.4로, raw model 대비 2.5% 올랐을 뿐이다. 데이터를 대량으로 추가해도 성능 향상은 1.0 percentage point에 그쳤다.
같은 10% 예산에서 trajectory를 무작위로 고른 Random-10%는 39.6으로 raw model보다 오히려 2.0% 낮아졌다. 이는 성공 trajectory 중에서도 학습에 해가 되는 데이터가 있다는 신호다.
반면 SWE-Prime이 고른 10% subset은 51.4를 기록했다. raw model 대비 27.2% 상승이고, 전체 성공 trajectory SFT보다 10.0 percentage point 높다. 10%가 약 3,216개 trajectory라고 하면, 3,216개로 32,161개를 이긴 것이다. 전체 SFT 대비 상대 상승은 약 24.2%로, 논문 초록이 말하는 최대 상승 폭에 해당한다.

Stage 2의 역할도 Table 1에서 수치로 확인된다. GLM-4.7-Flash에서 Stage 1만 쓴 w/o Stage 2는 SWE-Bench Verified 43.6이다. SWE-Prime의 51.4와 비교하면 같은 10% trajectory를 썼는데도 7.8 percentage point 차이가 난다. 이 차이는 loss mask를 통해 unselected segment의 gradient를 막은 효과다.
평균 interaction turn도 함께 줄어든다. GLM-4.7-Flash의 SWE-Bench Verified에서 전체 SFT는 67.9 turn, SWE-Prime은 56.0 turn이다. solved rate가 낮아진 것이 아니라 높아졌는데 turn이 줄었으므로, 단순히 일찍 포기한 것이 아니라 더 적은 행동으로 더 많이 해결한 효율성 개선으로 해석할 수 있다.

Hyperparameter 분석 Figure 4도 같은 결론을 보여준다.
Qwen3-Coder-30B-A3B-Instruct를 SWE-Bench Verified에서 평가했을 때, Stage 1만 쓴 상태에서 trajectory retention ratio를 5%로 하면 46.2, 10%로 하면 50.2, 20%에서는 49.6, 30%에서는 49.2가 나온다. 10%에서 정점이 나타나고 이후로는 오히려 낮아진다. 데이터가 너무 적으면 coverage가 부족하고, 10%를 넘기면 낮은 품질 또는 중복된 supervision이 다시 유입된다고 볼 수 있다.
retention ratio를 10%로 고정한 뒤 segment score threshold를 올려 보면 threshold 5에서는 46.8, 7에서는 53.2로 상승한다. threshold 8에서는 49.6, 9에서는 47.0으로 다시 떨어진다. threshold가 너무 낮으면 저품질 segment가 loss에 남고, 너무 높으면 유용한 segment까지 잘려나간다. 이 실험이 10% retention ratio와 threshold 7이라는 최종 설정을 정당화한다.

## 실험과 결과

학습 데이터는 Nebius가 공개한 SWE-rebench OpenHands Trajectories dataset이다. 이 dataset은 67,074개의 trajectory를 포함하며, 그중 32,161개가 issue를 성공적으로 해결한 resolved trajectory다. trajectory는 Qwen3-Coder-480B-A35B-Instruct가 OpenHands 환경에서 생성했다. SWE-Prime은 이 32,161개의 resolved trajectory를 후보 pool로 삼아 10% subset을 선택한다.

평가 모델은 GLM-4.7-Flash, Qwen3-30B-A3B-Instruct-2507, Qwen3-Coder-30B-A3B-Instruct 세 가지다. 평가 벤치마크는 SWE-Bench Verified 500개 task와 SWE-Bench Pro의 public split 731개 task다. 지표는 Resolved Rate, raw model 대비 상대 향상 Rel. Imp., 평균 interaction turn이다. 주요 baseline은 raw model, 전체 32,161개의 resolved trajectory로 SFT한 Resolved-Trajectory SFT, 같은 10% 예산에서 무작위로 고른 Random-10%다.

학습 설정은 최대 sequence length 131,072, batch size 32, AdamW optimizer, cosine learning rate schedule, peak learning rate $4\times 10^{-6}$이다. SWE-Prime을 제외한 baseline들은 동일한 cross-entropy objective를 쓰고, SWE-Prime만 selected segment의 assistant token에만 loss를 적용한다. 평가 시에는 task당 최대 100 interaction turn까지 허용하고, 각 모델의 기본 sampling 설정을 유지한다.

SWE-Prime은 모든 모델과 모든 벤치마크에서 가장 높은 Resolved Rate를 기록했다.
Qwen3-30B-A3B-Instruct-2507의 SWE-Bench Verified raw 25.2에 비해 SWE-Prime은 39.6으로 57.1% 상승했다. 같은 모델의 SWE-Bench Pro는 raw 8.21에서 SWE-Prime 18.88로 130.0% 상승했다.
GLM-4.7-Flash는 SWE-Bench Verified raw 40.4에서 SWE-Prime 51.4로 27.2%, SWE-Bench Pro raw 11.22에서 26.95로 140.2% 상승했다.
Qwen3-Coder-30B-A3B-Instruct는 SWE-Bench Verified raw 44.8에서 53.2로 18.8%, SWE-Bench Pro raw 29.55에서 34.75로 17.6% 상승했다.

전체 resolved trajectory SFT와 비교하면 10% subset이 모든 경우에서 더 좋다.
예를 들어 Qwen3-30B-A3B-Instruct-2507의 SWE-Bench Pro에서 전체 SFT는 16.83인데 SWE-Prime은 18.88로 약 12.2%의 상대적 향상이 있다.
GLM-4.7-Flash의 SWE-Bench Verified에서는 전체 SFT 41.4 대비 SWE-Prime 51.4로 약 24.2%의 상대적 향상이 있다.
Random-10%는 많은 setting에서 전체 SFT보다 낮고 raw model보다도 낮아지는 경우가 있어, 단순한 데이터 양 감소가 아니라 선택 품질이 성능 차이의 원인임을 보여준다.

Stage 2의 기여도 확인을 위해 trajectory-level selection만 적용한 w/o Stage 2와 비교했다.
모든 평가 setting에서 SWE-Prime이 w/o Stage 2보다 높다.
예를 들어 GLM-4.7-Flash의 SWE-Bench Verified에서 w/o Stage 2 43.6, SWE-Prime 51.4다.
Qwen3-30B-A3B-Instruct-2507의 SWE-Bench Verified에서 w/o Stage 2 34.6, SWE-Prime 39.6이다.
이는 trajectory-level filtering만으로는 좋은 trajectory 안의 저품질 행동을 다 제거하지 못한다는 point를 보여준다.

SWE-Bench Pro의 언어별 결과에서도 SWE-Prime은 Python, JavaScript, TypeScript, Go 모두에서 세 모델 기준 가장 좋은 성능을 기록했다.
예를 들어 Qwen3-30B-A3B-Instruct-2507의 Python은 raw 12.78, 전체 SFT 25.19, SWE-Prime 27.44다.
Go는 raw 2.50, 전체 SFT 7.86, SWE-Prime 10.00이다.
이는 HDBSCAN 기반 대표성 selection이 특정 issue type에 치우치지 않고 다양한 언어와 issue 분포를 유지하는 데 기여했음을 시사한다.

RQ3의 behavioral analysis에서는 process quality와 interaction efficiency가 함께 좋아졌다.
SWE-Prime으로 학습한 모델은 전체 SFT보다 최대 0.188만큼 redundancy를 줄였고, observe-before-edit rate는 최대 9.6 percentage point 올랐으며, tool success rate는 최대 0.094 올랐다.
평균 interaction turn은 여섯 평가 setting 모두에서 4.1 turn에서 12.7 turn 줄었다.
Resolved Rate가 동시에 올랐으므로 turn 감소는 일찍 포기해서가 아니라 더 집중된 문제 해결 경로를 학습했기 때문으로 볼 수 있다.

## 한계

저자가 명시적으로 한계 섹션을 따로 두지는 않았지만, 방법과 실험 설정에서 몇 가지 제한이 드러난다.
첫째, 10% trajectory retention ratio와 segment score threshold 7은 Qwen3-Coder-30B-A3B-Instruct와 SWE-Bench Verified를 기준으로 정해졌다. 논문은 이후 모든 모델과 벤치마크에 그 설정을 고정해도 효과가 유지된다고 보여주지만, 완전히 새로운 trajectory pool이나 다른 도메인에서도 이 값이 최적인지는 알 수 없다.
둘째, result quality와 segment scoring에 reference patch가 필요하다. reference patch는 정답 또는 사람이 검증한 patch인데, 실제 대규모 데이터 수집 상황에서는 항상 존재하지 않을 수 있다. 또 reference patch가 있다면 그 자체로 학습 신호가 될 수 있지만, 여기서는 어디까지나 selection에만 활용된다.
셋째, semantic segmentation과 segment scoring을 LLM에 의존하므로 LLM 판단의 noise와 비용이 발생한다. segment scoring 기준인 기여도, learnability, risk는 해석이 다소 주관적일 수 있고, 같은 segment라도 scoring에 따라 mask 결과가 달라질 수 있다.
넷째, tool call 실패, 인접 중복, git hacking detection은 비교적 단순한 규칙 기반 신호다. 이 규칙들이 잡지 못하는 다른 위험 행동이나 미묘한 over-edit, 불필요한 context exploration은 여전히 남을 수 있다.
다섯째, 학습 trajectory pool이 단일 teacher model인 Qwen3-Coder-480B-A35B-Instruct가 만든 데이터라는 점도 한계다. SWE-Prime이 선택한 subset은 그 teacher의 행동 분포 안에서 좋은 demonstration일 뿐, 다른 teacher나 다른 스타일의 유용한 trajectory까지 포괄한다고 단정하기 어렵다.

## 왜 중요한가

이 논문은 coding agent SFT에서 "데이터를 많이 모으는 것"보다 "무엇을 학습 신호로 쓸 것인가"가 더 중요할 수 있음을 보여준다. 32,161개의 성공 trajectory 전체로 학습한 것보다 10%인 약 3,216개를 신중히 선택해 학습한 모델이 더 높은 성능을 낸다는 결과는, 데이터 양을 늘리는 기존 접근의 diminishing return을 실증적으로 드러낸다.
실무적으로는 SFT에 필요한 GPU 계산과 데이터 저장 비용을 크게 줄일 수 있다는 의미가 크다. 전체 trajectory를 학습하는 대신 10%만 학습하고도 더 나은 모델을 얻을 수 있다면, 작은 팀도 고품질 coding agent를 fine-tuning할 여지가 생긴다.
또한 task success라는 outcome 지표만으로는 demonstration의 질을 판단할 수 없다는 교훈을 준다. SFT를 준비하는 실무자는 최종 테스트 통과 여부뿐 아니라 observe-edit-verify 패턴, tool call 안정성, 중복 행동, git leakage, patch scope, issue 다양성 같은 process·result·representativeness 지표를 설계해야 한다.
semantic segment 단위의 loss masking은 software issue 해결을 넘어 웹 탐색, 컴퓨터 사용, 장기 planning 같은 long-horizon agent SFT에도 적용 가능한 일반적인 아이디어다. 전체 trajectory에서 일부 구간만 학습 목표로 삼는 방식은 중간에 피할 수 없는 탐색이나 실패가 포함된 demonstration을 더 안전하게 활용하는 방법이 될 수 있다.
마지막으로 이 연구는 향후 process supervision, segment-level reward model, demonstration 품질 자동 평가 같은 후속 연구의 출발점이 된다. 결과가 아니라 결과에 이르는 행동의 학습 가치를 평가하는 data-centric 관점을 coding agent 분야에 구체적인 방법으로 연결했다는 점에서 중요하다.

## 원문 초록

> To improve large language models' ability to resolve real-world software issues, prior work has focused on constructing large-scale agent trajectory datasets and performing supervised fine-tuning (SFT) on successful trajectories. However, task success does not guarantee high-quality supervision: successful trajectories may still contain ineffective, redundant, or risky steps. Directly using such trajectories for SFT can introduce noisy supervision and encourage models to imitate undesirable problem-solving behaviors. Therefore, we propose SWE-Prime, a multi-granularity, two-stage SFT data selection method that progressively filters training data at the trajectory and segment levels. Specifically, the first stage performs trajectory-level screening based on process quality, result quality, and data representativeness, selecting a high-quality and representative subset of successful trajectories. The second stage performs segment-level selection by grouping consecutive steps into semantic segments and assessing each segment based on its contribution to the final solution, learnability, and potential risks. During SFT, all segments remain in the sequence to preserve context, while only selected segments contribute to the loss computation. Experiments on SWE-Bench Pro and SWE-Bench Verified show that training on the 10% trajectory subset selected by SWE-Prime outperforms training on the full resolved dataset, yielding relative performance gains of up to 12.2% and 24.2%, respectively.
