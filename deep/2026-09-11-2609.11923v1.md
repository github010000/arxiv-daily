## 한 줄 요약

GPU-CFR은 고정된 게임 트리를 한 번 컴파일하여 static dataflow로 변환하고 CUDA Graph Replay를 적용함으로써, tabular CFR의 반복 시간을 기존 GPU 대비 최대 80배, 빠른 CPU 구현 대비 최대 258배 단축한 시스템이다.

## 핵심 개념 풀이

**Extensive-form game과 information set**  
불완전 정보 게임은 플레이어가 상대방의 숨은 정보 때문에 자신이 정확히 어떤 상태에 있는지 모르는 상황을 다룬다. 게임에서 하나의 history는 루트부터 현재까지 일어난 모든 행동과 chance 사건의 기록인데, 포커에서 내 패는 알지만 상대 패는 모를 때, 상대 패만 다른 여러 history는 내 관점에서 구분할 수 없다. 이렇게 서로 구분할 수 없는 history들의 집합을 information set이라고 부르며, 한 information set에 속한 모든 history는 동일한 행동 선택지를 공유한다. 솔버는 각 information set마다 행동 확률 분포를 학습해야 하므로, information set의 개수가 게임 크기를 나타내는 핵심 지표가 된다. 예를 들어 heads-up no-limit hold'em 턴 서브게임은 information set이 83,040개에 달한다.

**Counterfactual regret minimization (CFR)**  
CFR은 불완전 정보 게임에서 내쉬 균형을 찾는 반복적 자기 대국 알고리즘이다. 매 iteration마다 두 번의 트리 순회를 수행한다. 먼저 forward reach pass에서는 루트에서 시작해 각 history에 도달할 확률(reach probability)을 곱해 나가며 계산한다. 이어서 backward value pass에서는 종단 보수를 거꾸로 접어 올리면서 각 행동의 기대 가치를 구한다. 그런 다음 각 information set의 행동에 대해 counterfactual regret, 즉 "그 행동을 했더라면 다른 행동들보다 얼마나 더 좋았을까"를 누적한다. 마지막으로 regret matching이라는 규칙으로 후회가 큰 행동에 더 높은 확률을 부여한 새 전략을 만든다. 평균 전략은 iteration이 진행될수록 내쉬 균형에 수렴한다. CFR+는 regret을 음수로 클램핑하는 변형으로 실제 수렴 속도가 훨씬 빠르다.

**CUDA Graph와 kernel launch overhead**  
GPU에서 하나의 커널은 보통 수 마이크로초 안에 끝난다. 하지만 CPU가 그 커널을 호출하고 프레임워크가 dispatch하는 데는 수십 마이크로초 이상이 걸릴 수 있다. 따라서 작은 커널이 많으면 GPU는 실제 연산보다 대기 상태로 있는 시간이 길어지는 launch-bound 상태가 된다. CUDA Graph는 커널 실행 시퀀스를 한 번 녹화해 두었다가, 이후에는 그래프 전체를 단 한 번의 graph launch로 재생할 수 있게 해 준다. 이렇게 하면 커널 사이의 launch overhead와 dispatcher overhead가 거의 사라진다. 단, 그래프 안에서 버퍼 주소나 shape가 바뀌면 안 되므로, 실행 시퀀스가 완전히 고정되어 있어야만 CUDA Graph를 사용할 수 있다.

**Static dataflow compilation**  
일반적인 CFR 구현은 매 iteration마다 게임 트리 인터페이스를 통해 노드를 하나씩 방문하며 포인터를 따라가고, 노드 타입에 따라 분기한다. 이는 제어 흐름이 매번 동적으로 결정되는 방식이다. GPU-CFR은 게임이 고정되어 있으면 이 모든 구조가 첫 iteration 전에 이미 알려져 있다는 점에서 출발한다. 그래서 빌드 타임에 게임을 한 번 순회하여 모든 edge, 정보 집합, 깊이 정보를 평평한 배열로 변환하고, 각 연산에 필요한 인덱스를 미리 계산한다. 이후 iteration은 이 고정된 배열에 대한 정해진 연산 시퀀스가 된다. 이렇게 만든 dataflow는 static하다고 부르며, shape와 인덱스가 절대 변하지 않아 CUDA Graph로 캡처할 수 있는 기반이 된다.

**Depth-level execution blocks**  
트리에서 forward pass는 부모의 reach가 자식의 reach에 필요하기 때문에 의존성을 지켜야 한다. 그런데 트리에서는 모든 자식이 부모보다 정확히 한 깊이 아래에 있다는 성질이 있다. 따라서 부모 깊이가 같은 edge들을 묶으면, 한 블록 안의 edge들은 서로 독립적이므로 병렬로 처리할 수 있고, 블록들을 깊이 순서대로 실행하면 전체 의존성이 충족된다. 이렇게 하면 순차적으로 실행해야 하는 단계의 수가 트리의 최대 깊이와 같아진다. 논문의 벤치마크 게임들에서는 깊이가 4에서 15 정도이므로, 단계 수가 매우 작아진다. 기존 방식은 stage와 depth를 교차하여 최대 100개의 블록을 만들었는데, depth-level execution blocks는 이를 트리 깊이로 줄인다.

**Dual-lane reach buffer와 sentinel slot**  
reach probability는 각 플레이어별로 따로 계산해야 한다. 플레이어 i의 reach는 i 자신의 행동 edge에서만 전략 확률을 곱하고, 상대방이나 chance edge에서는 그대로 복사해야 한다. 이 조건 분기를 없애기 위해 전략 벡터에 항상 1.0 값을 갖는 sentinel slot을 추가한다. 각 edge에 대해 플레이어별로 참조할 슬롯 인덱스를 빌드 타임에 정해둔다. 자신의 edge이면 실제 슬롯, 아니면 sentinel을 가리키게 한다. 그러면 런타임에는 분기 없이 해당 인덱스의 값을 읽어 곱하기만 하면 된다. 또한 두 플레이어의 reach 버퍼를 하나의 배열에 연속적으로 배치(dual-lane)하여, 한 번의 gather, multiply, scatter로 두 lane을 동시에 갱신한다. regret accumulation에서도 sentinel을 사용해 마지막 edge 분기를 제거한다.

## 문제의식

기존 GPU CFR 구현이 CPU보다 느렸던 이유는 실행 모델 자체에 있었다. CFR iteration은 게임 트리의 모든 노드를 수백만 개의 작고 의존적인 단계로 방문하는데, 각 단계는 포인터를 따라가고 노드 타입에 따라 분기한 뒤 몇 개의 float만 갱신한다. 이는 데이터 의존적 gather/scatter 패턴이라서 GPU의 넓은 병렬성을 활용하기 어렵고, 메모리 접근도 불규칙해진다. 반면 CPU는 이런 pointer chasing에 최적화되어 있어서, 오랫동안 tabular CFR의 최고 성능은 CPU 구현이 차지했다.

GPU에서 문제는 더 심각하다. 각 커널이 마이크로초 단위로 끝나기 때문에, 커널 launch와 프레임워크 dispatch가 실행 시간을 지배한다. 실제로 이전 GPU CFR 구현 중 가장 빠른 Kim(2026)의 sequence-form sparse product 방식도 같은 A100에서 HUNL turn 게임 기준 11.893 ms/iteration으로, 최적화된 CPU 구현에 비해 전혀 빠르지 않았다. Kim의 구현은 CUDA Graph로 캡처조차 할 수 없었는데, cuSPARSE 호출이 stream capture를 거부하고, 레벨별 row slicing과 index assignment가 매 iteration마다 host와 device 사이에 데이터를 이동시켰기 때문이다.

이 문제가 실제로 중요한 이유는 게임 솔버의 시간 제약 때문이다. 현대 게임 에이전트는 플레이 중에 수천만 상태의 게임 트리를 몇 초 안에 풀어야 한다. tabular CFR은 포커, 협상, 보안 게임 등에서 표준 솔버로 쓰이며, subgame re-solving, abstraction refinement, neural CFR 등 많은 방법의 내부 루프를 구성한다. 그런데 iteration 시간이 느리면 에이전트가 할 수 있는 일의 한계가 결정된다. 그래서 과거 대규모 포커 시스템들은 GPU를 포기하고 슈퍼컴퓨터급 CPU 병렬성을 사용했다. GPU-CFR은 이 실행 계층의 비용을 근본적으로 줄이고자 한다.

## 핵심 아이디어

핵심 관찰은 고정된 게임에 대해 CFR iteration에서 수치 값만 변하고 나머지 모든 구조는 변하지 않는다는 것이다. 트리 토폴로지, information set, chance 행동, 텐서 shape, 데이터 의존성은 첫 iteration 전에 이미 결정되어 있다. 따라서 게임을 마치 프로그램처럼 취급하여 한 번 컴파일하면, iteration을 고정된 depth-level batched 연산 시퀀스로 표현할 수 있다. 이 시퀀스의 shape와 인덱스가 변하지 않으므로 CUDA Graph로 캡처하여 한 번의 graph launch로 재생할 수 있다.

이 아이디어가 문제를 푸는 논리는 두 갈래다. 첫째, 컴파일된 표현이 pointer chasing과 동적 분기를 제거하고 데이터 병렬 연산으로 바꾸어 실제 작업량을 크게 줄인다. static chance folding은 전략과 무관한 chance 계산을 빌드 타임으로 옮기고, depth-level execution blocks는 순차 단계를 트리 깊이로 제한하며, dual-lane reach buffer와 sentinel slot은 마지막 edge 분기까지 없앤다. 이로써 프레임워크 연산 수가 최대 18.1배 감소한다. 둘째, CUDA Graph Replay가 kernel launch와 dispatcher overhead를 제거하여 작은 커널들이 GPU에서 연속적으로 실행되게 한다. 이렇게 하면 GPU가 실패했던 두 원인, 즉 launch overhead와 불규칙한 접근을 동시에 해결한다. 결과적으로 iteration 시간이 거의 트리 크기에 무관하게 일정해진다.

논문은 이 두 효과를 분리하여 측정한다. 컴파일된 표현 자체만으로도 CPU 8 스레드에서 GPU baseline보다 2.2~51.1배 빠르다. 그래프 재생은 여기에 1.6~3.6배 추가 가속을 더한다. 즉, 성능 향상의 대부분은 표현 변경에서 오고, CUDA Graph는 그 위에 dispatch 비용을 제거하는 역할을 한다.

## 방법

**1단계: 게임 컴파일**  
컴파일러는 게임을 BFS(너비 우선) 순서로 한 번 순회하여 부모가 항상 자식보다 앞에 오도록 노드에 번호를 매긴다. 각 노드에 대해 소유자(플레이어 1, 2, chance, terminal), 깊이, 종단 보수를 저장하는 node array를 만든다. 각 edge에 대해서는 부모 노드, 자식 노드, slot index를 기록한다. 여기서 slot은 (information set, action) 쌍의 평평한 인덱스를 의미하며, chance edge는 고정 확률만 갖고 slot은 없다. information set별로 action 수와 slot offset을 저장하여, regret matching이 flat vector에서 segment reduction으로 동작하도록 한다. 모든 solver state(누적 regret, 전략 합, 스크래치)는 사전 할당된 device tensor에 저장되고, 루트 reach는 1로 초기화된다.

**2단계: static chance folding**  
chance 노드는 전략과 무관하므로, 각 노드 h에 대해 루트에서 h까지 chance 확률의 곱 $\pi_c(h)$를 빌드 타임에 계산할 수 있다. 이 값을 이용해 values template $v_{\mathrm{tmpl}}(h) = \pi_c(h) \cdot u(h)$ (종단 노드면, 아니면 0)을 만든다. backward pass는 매 iteration마다 이 템플릿에서 시작한다. 동적 pass에서는 모든 chance edge가 multiplier 1로 취급되는데, 이는 sentinel slot이 그 역할을 한다. 이렇게 하면 forward pass에서 chance 곱셈이 완전히 제거되고, backward pass의 결과는 chance-weighted continuation value가 된다. 각 종단의 전체 경로 chance 확률 곱은 템플릿에서 정확히 한 번만 들어가므로 이중 계산이 없다.

**3단계: depth-level execution blocks**  
forward pass는 부모 깊이를 기준으로 edge를 그룹화한 블록들을 깊이 순서대로 실행한다. 각 블록은 하나의 batched gather, multiply, scatter로 구현된다. 예를 들어 한 블록에서 reach buffer의 부모 위치 값을 gather하고, 해당 edge의 전략 factor를 gather하여 곱한 뒤, 자식 위치에 scatter한다. backward pass는 같은 블록을 역순으로 사용하며 index_add scatter를 쓴다. index_add는 같은 인덱스에 여러 기여가 도착하면 더해 주는 연산이라, 한 부모가 여러 자식을 가질 때 적합하다.

**4단계: dual-lane reach buffer와 sentinel slot**  
전략 벡터 $\sigma$에 마지막에 항상 1을 갖는 sentinel slot을 추가한 $\sigma_{\mathrm{ext}}$를 사용한다. reach buffer는 크기 2N으로 두 플레이어 lane을 연속적으로 배치한다. 각 edge와 각 lane에 대해 참조할 slot index를 빌드 타임에 결정한다. 자신의 행동 edge이면 실제 slot, 그렇지 않으면 sentinel을 가리킨다. forward pass는 한 줄의 연산 $\pi[C_2] \leftarrow \pi[P_2] \cdot \sigma_{\mathrm{ext}}[S_2]$로 두 lane을 동시에 갱신한다. 여기서 $P_2, C_2, S_2$는 해당 블록의 부모, 자식, 슬롯 인덱스 배열이다. regret accumulation에서도 유사하게, 각 decision edge의 기여를 slot에 index_add로 누적한다. 상대방 reach는 미리 계산된 opponent-reach lane 인덱스를 통해 읽는다.

**5단계: iteration 데이터플로우**  
한 번의 CFR+ iteration은 다음 순서로 진행된다. 먼저 regret matching 단계에서 누적 regret $R$을 clamp하여 positive regret을 얻고, information set별 합산으로 정규화하여 새 전략 $\sigma$를 만든다. sentinel slot은 항상 1로 유지된다. 이어서 forward pass에서 depth 1부터 D까지 dual-lane 연산을 수행해 두 플레이어의 reach를 채운다. backward pass에서는 $v \leftarrow v_{\mathrm{tmpl}}$로 초기화하고, depth D부터 1까지 index_add로 value와 regret을 누적한다. 마지막으로 decision edge들에 대해 평균 전략 accumulator $\bar{s}$에 현재 전략을 reach 가중치를 곱해 더하고, CFR+이면 $R \leftarrow \max(R, 0)$을 적용한다. 전체 연산 수는 상수 부분과 깊이에 비례하는 부분으로 구성되어, 게임 크기와 무관하게 64~152개 정도로 고정된다.

**6단계: CUDA Graph Replay**  
전체 iteration을 CUDA Graph로 캡처한다. 선형 평균 가중치 $w_t = t$는 매 iteration 변하므로 static graph가 직접 볼 수 없다. 이 문제는 $w$를 0차원 device tensor에 저장하고, 캡처된 body 안에서 연산 후 in-place로 증가시키는 방식으로 해결한다. replay batch 전에 host가 정확한 시작 인덱스를 채워 넣는다. 캡처 전에는 side stream에서 warmup iteration을 수행하고, 캡처 시 모든 지속 버퍼의 데이터 포인터를 기록하여 이후에 버퍼가 재할당되면 replay를 거부한다. capture가 실패하면 eager execution으로 자동 fallback하며, fallback은 같은 커널을 같은 순서로 실행하므로 동일한 float 결과를 낸다. 그래프 재생은 eager보다 1.6~3.6배 빠르게 만든다.

## 왜 성립하는가

논문은 컴파일된 iteration의 정확성과 최적성을 몇 개의 명제로 증명한다. **Proposition 1 (folded chance exact)** 은 chance 확률이 경로 곱으로 상수이므로 values template에 접으면 각 terminal의 chance product가 정확히 한 번만 backward pass에 들어감을 보인다. 동적 pass에서 chance multiplier를 1로 두어도 수학적으로 동일한 기대값을 계산한다는 것이다. 직관적으로, chance 노드는 전략과 독립적이므로 미리 계산해 두어도 결과가 변하지 않는다.

**Proposition 2 (dual-lane exact)** 는 sentinel slot이 항상 1이므로, true slot을 참조하면 전략 곱이 되고 sentinel을 참조하면 1 곱셈이 되어 복사와 동일함을 보인다. slot map은 빌드 타임에 결정되므로 런타임에 어떤 분기도 평가하지 않으면서 Eq. (7)의 조건부 정의를 정확히 만족한다. 이는 분기 없는 코드가 원래 조건부 계산과 동일함을 보장한다.

**Proposition 3 (depth schedule shortest)** 는 의존성 제약 때문에 어떤 스케줄도 최소 트리의 최대 깊이 $D$만큼의 그룹이 필요함을 보인다. 부모 깊이로 그룹화한 partition은 정확히 $D$개 그룹을 만들고, 각 그룹 내 edge들은 서로 독립적이므로 유효한 의존성 지킴 스케줄이다. 따라서 연산자 호출 수는 $c_1 + c_2 D$로 최소가 된다. 이 성질 덕분에 iteration 시간이 트리 크기보다 깊이에만 의존하게 된다.

**Proposition 4 (averaging horizon)** 는 linear averaging에서 누적합이 $O(T^2)$로 증가하는 반면 각 항은 $O(T)$이므로, float32에서는 $T$가 커지면 새 항이 누적합의 ulp보다 작아져 반올림 손실이 발생함을 보인다. 이는 왜 average strategy accumulator를 float64로 유지하는지 설명한다. 다른 버퍼는 float32를 쓰지만, 이 누적기는 정밀도가 중요하므로 별도로 처리한다.

직관적으로, 트리를 깊이별로 묶으면 각 레벨의 모든 edge가 독립적이므로 GPU가 한 번에 처리할 수 있고, 레벨 수가 트리 깊이와 같아서 순차 단계가 매우 적어진다. 이는 framework dispatch 수를 크게 줄인다. CUDA Graph Replay는 이 고정된 시퀀스를 한 번의 launch로 실행하므로 kernel launch overhead가 거의 사라진다. 두 메커니즘이 결합하여 GPU에서 흔히 발생하는 launch-bound 문제를 해소한다.

## 구체적 예시

논문의 Figure 2와 Figure 3은 11노드짜리 작은 게임에서 컴파일 파이프라인을 보여준다. 이 게임은 chance root, 두 플레이어 각각 두 번의 decision, 그리고 여섯 개의 terminal을 가진다. 컴파일은 BFS 순서로 노드에 번호를 매기고, edge, information set, depth 정보를 평평한 배열로 변환한다. Figure 3은 이 게임에서 compiled CFR+ iteration이 실행 순서대로 쌓여 있는 모습을 보여준다. forward pass에서 depth 1 블록은 chance edge들을 처리하는데, chance edge는 sentinel slot(1)을 곱하므로 사실상 복사에 해당한다. depth 2 블록에서는 플레이어 1의 edge들이 실제 전략 슬롯을 곱하고, 플레이어 2 lane은 sentinel로 복사된다. 이렇게 두 lane이 한 번의 연산으로 동시에 갱신된다. backward pass에서는 terminal에서 시작해 depth 역순으로 value를 index_add로 누적한다.

표 2의 HUNL river 게임(Information set 3,000개, States 137,415개)을 보면, reference implementation은 execution blocks 27개, Aten operations 501개를 사용한다. 반면 compiled dataflow는 blocks 4개, operations 64개로 줄어든다. 7.8배의 연산 수 감소다. 왜 4개인가? 이 게임의 트리 깊이가 4이므로 depth-level blocks가 정확히 4개가 된다. reference는 stage와 depth의 교차(intersection)로 블록을 만들어서 27개가 된 것이다. 더 극단적인 HUNL turn 게임에서는 reference가 100 blocks, 1,742 operations인데 compiled는 8 blocks, 96 operations로 18.1배 감소한다. 이 예시는 depth-level grouping이 얼마나 효과적으로 framework dispatch를 줄이는지 보여준다.

C++ 단일 스레드 구현인 LiteEFG가 Kuhn(54 Information set)에서 0.008 ms/iteration으로 GPU-CFR graph의 0.113 ms보다 훨씬 빠른 것도 흥미롭다. 이는 GPU의 고정 launch floor 때문이다. 게임이 너무 작으면 GPU가 launch overhead를 상쇄할 만큼 충분한 병렬 작업을 가지지 못한다.

## 실험과 결과

**속도 비교 (표 3)**  
논문의 주요 타이밍 결과를 표 3에서 인용한다. HUNL turn 서브게임(83,040 Information set)에서 GPU-CFR graph는 0.397 ms/iteration, eager는 0.617 ms, Kim(2026) GPU는 11.893 ms, LiteEFG(CPU)는 102.160 ms, OpenSpiel(Python)은 n/a로 기록되었다. GPU-CFR graph는 Kim 대비 약 29.9배, LiteEFG 대비 약 257배 빠르다. 논문이 보고한 29.8~80.4배 범위의 하한에 해당하는 게임이다. 전체 8게임에서 GPU-CFR graph는 Kim 대비 중앙값 44.1배 빠르다. eager 컴파일만으로도 17.4~23.5배 빠르므로, 성능 향상의 대부분은 컴파일 표현에서 온다.

CPU 8 스레드로 컴파일된 솔버를 실행해도 Kim A100 GPU보다 모든 게임에서 2.2~51.1배 빠르다. 이는 컴파일된 표현 자체가 GPU baseline보다 훨씬 효율적임을 보여준다. 그래프 재생은 eager 대비 1.6~3.6배 추가 가속을 준다. 작은 Kuhn에서는 GPU-CFR graph 0.113 ms 대 LiteEFG 0.008 ms로 LiteEFG가 14배 빠르지만, 중대형 게임에서는 GPU-CFR이 압도한다.

**확장성 (Figure 5)**  
HUNL turn 게임에서 플레이어당 핸드 수 K를 4에서 24로 늘리면 States가 46k에서 1.76M으로 37.9배 증가한다. 그런데 iteration time은 2.95배 증가에 그친다. 이는 노드 수가 늘어도 트리 깊이가 거의 변하지 않아서 operation sequence가 고정되고 각 operation의 폭만 넓어지기 때문이다. 달성 대역폭은 최대 크기에서 A100 이론 피크의 5.5%에 불과하며, 이는 launch latency와 depth가 지배하는 워크로드임을 확인해 준다.

**시간 대 품질 (표 5, Figure 8)**  
표 5는 고정 exploitability 임계값에 도달하는 시간을 비교한다. Leduc에서 Kim의 30초 시점 exploitability의 10배 임계값에 도달하는 시간이 GPU-CFR은 0.115초, Kim은 1.015초로 GPU-CFR이 8.8배 빠르다. 3배 임계값에서는 0.198초 대 5.828초로 29.5배, 1.5배 임계값에서는 0.450초 대 16.971초로 37.7배 빠르다. Goofspiel, Liar's Dice, Battleship, HUNL river, HUNL turn에서도 유사한 경향이 나타난다. HUNL turn에서는 10배 임계값에서 3.8배, 3배에서 9.6배, 1.5배에서 18.2배 빠르다. 즉, 낮은 iteration 비용이 그대로 wall-clock 시간 단축으로 이어진다.

**특수 게임**  
Libratus endgame 4(96,159 Information set, 36M states)에서는 terminal이 대부분인 트리라서 GPU-CFR 200 iteration이 3.184초, Kim이 2.374초로 Kim이 약간 더 빠르다. 그런데 LiteEFG는 2,771.135초로 GPU-CFR이 870배 빠르다. 1,000 iteration에서도 GPU-CFR 13.941초, Kim 11.820초로 Kim이 여전히 빠르다. 이는 depth-dependent work가 적은 terminal-heavy tree에서 compiled schedule의 이점이 줄어들기 때문이다.

**프레임워크 연산 수**  
HUNL turn ablation에서 컴파일은 Aten operations를 18배 줄였고 시간은 19배 줄였다. 그래프 재생은 추가로 1.6배 줄여 총 29배 사다리를 만든다. Nsight trace에 따르면 eager 경로는 87개 kernel launch를 내보내고 GPU 사용률이 1/3에 불과하지만, graph replay는 1개 graph launch로 GPU 사용률이 94%에 도달한다.

## 한계

저자가 인정한 한계 중 하나는 GPU scatter reduction의 비결정성이다. GPU에서 scatter reduction 순서가 프로세스마다 달라질 수 있어서, 마지막 비트 차이가 발생하고 일부 실행에서 exploitability가 다른 군집으로 갈 수 있다. 논문의 HUNL river 서브게임에서 20회 동일 실행 중 4회가 두 번째 exploitability 군집(0.6% 차이)에 도달했다. 이는 float32 산술에서 reduction order에 민감한 결과로, 대규모 병렬 처리에서 피하기 어려운 특성이다.

작은 게임에서는 여전히 CPU 단일 스레드 구현이 더 빠를 수 있다. Kuhn(54 Information set)에서 LiteEFG가 0.008 ms/iteration으로 GPU-CFR graph 0.113 ms보다 14배 빠르다. GPU의 고정 launch floor가 작은 워크로드에서 불리하게 작용한다. 또한 terminal-heavy tree에서는 Kim(2026)의 sequence-form 방식이 GPU-CFR보다 빠를 수 있다. Libratus endgame 4에서 Kim이 200 iteration 기준 2.374초로 GPU-CFR 3.184초보다 빨랐다.

CUDA Graph capture가 모든 환경에서 지원되지 않을 수 있고, 실패하면 eager execution으로 fallback하여 속도 이점이 줄어든다. 또한 게임이 바뀔 때마다 컴파일이 필요한데, 논문은 첫 solve에서 비용이 회수된다고 주장하지만 매우 짧은 해결 시간이 요구되는 온라인 설정에서는 컴파일 overhead가 부담될 수 있다. float32 정밀도 이슈도 존재한다. linear averaging의 accumulator는 float64로 해결하지만, 다른 버퍼와 iteration 산술은 float32를 사용하므로 극도로 긴 iteration에서는 정밀도 문제가 생길 여지가 있다.

## 왜 중요한가

이 논문은 10년 넘게 CPU가 지배하던 tabular CFR 워크로드에서 GPU가 확실히 승리하는 첫 결과를 제시한다. 이는 단순히 하나의 알고리즘을 가속한 것이 아니라, 게임 솔버의 실행 계층 자체를 바꾸는 시스템적 기여다. tabular CFR은 포커, 협상, 보안 게임 등에서 표준 솔버로 쓰이며, subgame re-solving, abstraction refinement, neural CFR 등 많은 방법의 내부 루프를 구성한다. GPU-CFR의 컴파일된 sweep은 이 모든 방법에 그대로 적용될 수 있어서, 상위 알고리즘을 바꾸지 않고도 전체 시스템 속도를 획기적으로 높일 수 있다.

실무적 관점에서, 이전에는 슈퍼컴퓨터급 CPU 클러스터가 필요했던 오프라인 솔브가 이제 단일 GPU에서 가능해졌다. 비용과 접근성이 크게 개선된다. 또한 이 접근법은 "고정된 구조를 컴파일하여 launch overhead를 제거한다"는 일반 원리를 제시한다. 이는 게임 트리뿐 아니라 다른 불규칙한 그래프 기반 수치 워크로드에도 적용될 수 있는 패턴이다. 후속 연구를 위한 공개 코드와 벤치마크 스위트는 이 분야의 재현 가능성을 높이고, 향후 게임 솔버 하드웨어나 프레임워크 설계의 출발점이 될 수 있다.

## 원문 초록

> Counterfactual regret minimization (CFR) is one of the few large numerical workloads that still runs faster on CPUs than on GPUs. Each iteration sweeps a game tree with up to billions of states in millions of small, interdependent gather and scatter steps issued through a generic tree interface. On a GPU every kernel finishes in microseconds, so kernel launches and framework dispatch dominate the run time, and prior GPU implementations have lost to optimized CPU code. We observe that for a fixed game, everything about a CFR iteration except the numerical values is known before the first iteration runs. We propose GPU-CFR, a compiler and runtime built on this observation. It compiles any game once into static dataflow: flat edge and information-set arrays, precomputed indices, and depth-level batched passes fix the entire operation sequence, and only solver state changes between iterations. Static chance folding, depth-level execution blocks, and a dual-lane reach buffer cut the number of framework operations by up to 18.1x. Because shapes, indices, and buffer addresses never change, CUDA Graph Replay records the iteration once and replays it with a single graph launch. On one A100, across an eight-game suite that spans card games, dice games, and board games, GPU-CFR runs 29.8--80.4x faster than the fastest prior GPU CFR on the same accelerator, and 14--258x faster than LiteEFG, one of the fastest open-source CPU implementations, on the four largest games. The compiled representation carries most of that margin: on eight CPU threads with no accelerator it is already 2.2--51.1x faster than the GPU baseline. On the CPU the optimized path reproduces the reference iterates bitwise, and tree construction and graph capture pay for themselves within the first solve. GPU-CFR beats every CPU and GPU baseline on the mid-to-large games of the suite without changing the update rule.
